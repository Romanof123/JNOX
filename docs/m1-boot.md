# M1 AArch64 커널 부팅 벤치

한국어 · [English](m1-boot.en.md)

첫 소스 후보의 빌드 해시와 정상·실패 기동 결과는 독립 검증 기록에서 확인할 수 있다. [EVD-001 부팅 결과](evidence/evd-001.md)

`CHG-001`은 기획 기준선 `4ce1e16`에서 M1 커널의 첫 실행 단계를 도입한다. `IMP-001`은 AArch64 진입점, Rust 기동, 초기 UART 출력, CPU 대기 루프를 포함한다. P1 참조 에뮬레이터를 새로 기동할 때마다 동일한 독립 실행형 `no_std` 커널 ELF가 지정된 Rust 실행 지점에 도달하는지 확인하는 엔지니어링 벤치다. [M1 제품 범위](product-plan.md) · [개발 수명주기](lifecycle.md)

## UART 계약

QEMU `virt`에 TCG, Cortex-A72 CPU 1개, RAM 128 MiB를 구성하고 `-kernel`로 커널 ELF를 직접 전달한다. 첫 UART는 시험기에 연결하고 모니터와 화면을 끄며 에뮬레이터 진단은 별도로 수집한다. `READY`는 Rust가 BSS 검사 변수에서 기대값 0을 읽고 초기 UART 출력을 마쳤다는 뜻이다. 이후 서비스의 가용 여부는 각 서비스 시험에서 판정한다.

진입 코드는 BSS 검사 변수에 0이 아닌 값을 쓴 뒤 BSS를 지운다. Rust는 두 줄 중 첫 줄을 출력하기 전에 이 변수를 휘발성 읽기로 검사한다. 이 순서로 ELF 로더가 처음부터 메모리를 0으로 채웠을 때도 기동 코드가 검사 변수를 지웠는지 관찰할 수 있다. 두 줄을 출력하면 CPU는 `WFE` 루프에서 대기한다. 한 번의 정상 기동에서 수집할 UART 전체 출력은 다음 순서의 ASCII 두 줄이며, 각 줄은 LF 또는 CRLF로 끝난다.

```text
JNOX M1 BOOT
JNOX M1 READY
```

## 재현 절차와 판정

고정된 Rust 도구 체인, `aarch64-unknown-none` 타깃, Python 3, `qemu-system-aarch64`를 사용할 수 있는 셸에서 저장소 루트를 기준으로 실행한다.

```sh
cd kernel
cargo build --release --locked
cd ..
python3 tools/qemu_boot.py --kernel kernel/target/aarch64-unknown-none/release/jnox-kernel
```

1. **두 차례 초기 기동.** SHA-256이 같은 ELF를 두 번 기동한다. 매번 새 QEMU 프로세스를 띄우고 새 UART 기록을 시작한다. 각 기동에서 호스트 기준 기본 시한 5초 안에 두 줄이 모두 나와야 한다. 마지막 줄 이후 최소 100 ms 동안 QEMU가 계속 실행되며 추가 출력이 없는지 보고, 호스트에서 종료한 뒤 남은 바이트를 수집한다. 관찰 시간과 시한은 시험기 설정값이다. 게스트 기동 지연과 실보드 리셋 동작은 별도 시험에서 측정한다.
2. **거짓 합격 방지.** 마지막 줄 종결자까지 UART 전체 바이트열을 대조한다. 시한 초과, 에뮬레이터 조기 종료, 기동 오류, 줄 누락·역순·중복, 추가 바이트, 종결되지 않은 마지막 줄은 해당 기동의 실패다. 잘못된 입력과 커널이 기동할 수 없는 실행으로 판정기를 점검한다. 호스트 도구가 출력한 줄이 UART 판정에 쓰이지 않도록 진단은 별도 보관한다. `READY` 이후의 무출력은 관찰 구간에 한정된다. 그 원인을 `WFE` 대기로 판정할 때는 후보의 대기 루프도 검토한다.
3. **후보 식별과 재빌드.** 소스 리비전과 로컬 변경, 호스트, 컴파일러·링커 버전과 옵션, 타깃, 의존성 잠금 파일, QEMU 버전·인수, ELF SHA-256, 각 기동의 UART·진단·종료 사유를 기록한다. 같은 입력을 깨끗한 별도 빌드 디렉터리에서 재빌드해 ELF SHA-256을 대조한다. 둘 다 부팅되더라도 해시가 다르면 재현성은 미확인으로 남긴다. 새 검증자가 최초 블랙박스 판정과 로그를 고정한 뒤 구현 및 앞선 팀의 결과를 검토한다. 시험 증거는 이 계약과 별도로 기록한다. ## 스케줄러 작업 인계

식별된 부팅 ELF와 반복 가능한 부팅 시험을 회귀 검사용 기준선으로 인계한다. 고정 우선순위 디스패치를 시험하기 전에 첫 실행 스레드의 저장 문맥과 스택, 예외 벡터, 타이머·IRQ 설정과 확인 응답, 실제로 어느 스레드가 실행됐는지 구분할 관찰 방법을 정한다. 우선순위 선택, 같은 우선순위의 실행 순서, 선점에는 각자 기대 실행 순서와 실패 사례를 둔다. 태스크 수명주기, 스케줄링, 타이머, 격리, IPC는 후속 M1 과제다. 네이티브 앱, Linux 호환, SMP, 실보드 타이밍과 제품 안전 근거는 이 부팅 판정의 범위 밖이다.
