# 고정 다단계 큐와 누적 실행량 기반 피드백 큐

[English](m4-multilevel.en.md) · [변경 이슈 #50](https://github.com/Romanof123/JNOX/issues/50)

CHG-021 · POL-009 · REQ-002/005/023 → DES-003/012 → IMP-019 → VER-002/005/023. Cortex-A72 가상 CPU 한 개, GICv2, EL1 물리 타이머를 사용한다. 같은 실행의 소스·ELF 해시, UART, IRQ·SVC 및 디스패치 기록을 보존한다.

* **고정 큐.** 하위 클래스 작업 0을 준비시켜 두고 상위 클래스 A와 B가 실제 타이머 만료 네 번에 걸쳐 교대하게 한다. 매 결정에서 준비 순서와 복귀 주소를 확인한다. 상위 작업들이 차단된 뒤 하위 작업이 실행돼야 한다. 상위 작업이 계속 준비된 동안 이 구성의 하위 클래스에는 최소 서비스 할당이 없다.
* **피드백 큐.** 세 단계의 허용량은 각각 3·4·6단위다. 양보하는 작업, 대화형 작업 및 CPU를 계속 쓰는 작업을 함께 준비한다. 한 단위씩 소비한 두 번의 조기 양보를 측정하고, 양보 후에도 잔여 허용량이 이어지는지 확인한다. 세 번째 단위를 소비하면 강등되어 먼저 준비된 경쟁 작업이 앞선다. 누적 12단위의 주기적 부스트에서 단계 변화, 준비 순서 보존과 실제 다음 선택을 확인한다. 수면·깨우기 전후 상태와 소유자를 기록한다.
* **회계.** 정지할 때마다 허용량, 카운터 간격, 계상 단위, 단계 및 남은 허용량을 기록한다. 한 단위 미만과 처리기 시간의 계상 규칙을 명시한다. 타이머 및 자발적 양보 경로에서 전용 문맥이 저장·복구됨을 확인한다. 호스트에서는 독립 결정 기준과 잘못된 전이·중복 반환도 대조한다.

가상 시험은 이산 서비스와 실행 순서를 측정한다. 실물 상한, 제품 부하 및 시간 기준 승인은 별도 추적한다.

kernel에서 `cargo build --release --locked --features multilevel-bench -j1`, 저장소 루트에서 `python3 tools/qemu_boot.py --profile multilevel --kernel kernel/target/aarch64-unknown-none/release/jnox-kernel`를 실행한다. 최초 실행에서는 MULTILEVEL_CAPTURE_DIR를 새 경로로 두고 원래 인자를 python3 -B tools/multilevel_capture.py에 전달하는 Linux 실행 래퍼를 사용한다. 부팅 두 줄 이후 표식은 MLQ STRICT FOUR, MLFQ YIELDS DEMOTED, MLFQ BOOST ORDER, MULTILEVEL PASS 순서다. multilevel_witness 심볼은 1,376바이트다. 처음 u64 두 개는 행 수와 틱당 카운터 단위다. MLQ 7행, MLFQ 10행이 이어진다. 각 80바이트 행은 u64 7개(선점 PC·문맥 주소·선택 PC·발급 시각·반환 시각·타이머 만기·진행 카운터), 이어서 24바이트(사례·동작·호출자·선택자·허용량·사용량·누적 서비스·부스트·준비/실행 마스크·PPI·부스트 전후 각각 작업별 등급 3개와 잔량 3개·패딩 2개)다. 동작 1/2/3은 양보·차단·물리 IRQ다. PPI 30과 예외 복귀 주소를 ELF의 실행 루프 심볼에 대조한다. 틱은 카운터 주파수의 1/25이고 디스패치부터 예외까지 경과한 정수 틱을 허용량까지 계상한다.
