# 플랫폼 출시 체크리스트

[English](platform-checklist.en.md) · CHG-077 · AArch64 제품 계획

CAP-001~CAP-021에서 출시 프로파일에 필요한 기능을 선택한다. 각 항목에 담당 팀과 완료 판정에 필요한 관측 결과를 적었다. 해당 항목에 리비전, 이미지, 프로파일, 장치 또는 모델, 원시 결과와 독립 판정을 함께 기록한다. 최소 제어 이미지와 확장 서비스 이미지의 자원·인수 기록은 각각 관리한다. [기능 카탈로그](platform-capabilities.md) · [제품 마일스톤](product-plan.md)

**현재 근거.** AArch64 커널 이미지에 링크한 Rust 스레드가 실행된다. Pi 4 에뮬레이션에서는 두 번의 콜드부트 각각에서 특정 코어를 대상으로 한 깨우기 두 번과 중단된 작업으로의 복귀를 관측했다. 스케줄링 검증표에 정책별 검증 범위와 미결 사례가 있다. 별도의 가상 허가 신호 통합 시험에서는 20개 위치 중 운용 기준을 만족한 위치가 0개였다. 이 결과로 판정할 수 있는 범위는 해당 커널과 모델 사례다. 일반 IPC 서비스, 영구 매체, 실제 창 표시, 실보드 타이밍과 제품 안전에는 각각 별도 근거가 필요하다. [링크된 작업 런타임](fixed-runtime.md) · [모델 깨우기 근거](evidence/evd-056.md) · [스케줄링 검증표](scheduling-release-cases.md) · [허가 신호 시험](evidence/evd-054-integration.md)

별도의 AArch64 QEMU virt 최초 콜드부트에서 네이티브 v1 정적 C 프로세스 하나가 EL0에서 37을 계산하고 종료값 37을 전달했다. fd 1에 대한 쓰기 호출에서 커널은 −38(ENOSYS)을 반환했고 응용 표준 출력은 비어 있었다. 타깃 파일 입출력의 성공, POSIX 소스 프로파일 및 일반 프로세스 수명주기는 미검증이다. [네이티브 C 시작·종료 검증](native-el0-startup.md)

## 제품 담당자가 먼저 정할 네 가지

답은 [제품 결정 이슈](https://github.com/Romanof123/JNOX/issues/162)에 기록한다. 시스템팀과 기능안전팀이 선정된 용도를 바탕으로 시간·자원 한계의 근거를 마련하고 승인한다.

| 결정 | 적을 내용 |
| --- | --- |
| 첫 애플리케이션 | 입력과 출력은 무엇이며, 입력이 끊겼을 때 사람이나 장비가 어떤 동작을 보아야 하는가? |
| 시간 | 어떤 기록에 날짜가 필요한가? 다른 기기와 시각을 맞춰야 하는가? 날짜를 모르는 부팅 직후에도 어떤 동작을 허용하는가? |
| 데이터 | 전원이 갑자기 꺼져도 남아야 하는 설정·기록·로그는 무엇인가? 허용 손실과 복구 시간을 적고, 아직 모르는 값은 도출 대상으로 표시한다. |
| 화면·호환성 | 첫 화면과 입력 장치를 정하거나 화면 없는 구성을 선택한다. 안전과 관련된 표시, 실행할 기존 X11 앱과 바이너리 아키텍처가 있으면 적는다. |

## 하드웨어 구매 전

- [ ] **제품 책임자·시스템 팀.** 첫 사용 사례, 고장 시 안전 출력, 필요한 기한, 화면 사용 여부, 네트워크 용도, 전원 차단 후 보존해야 할 데이터를 정한다. 정확한 보드 리비전, 보드·안전 문서 확보 여부, 디버그 프로브·직렬·전원 차단 시험 접근성, 저장 매체, 선택한 화면·입력 장치 및 첫 네이티브 또는 재사용 드라이버를 확인한다. 구매 전 보드 담당자, 예산과 승인을 기록한다. Pi 4 모델은 포팅의 재현 가능한 출발점이다. [실보드 벤치 계획](boards/pi4-p1.md)
- [ ] **PM·검증 팀.** #21에 승인된 프로파일별 스케줄링 결과와 해당 보드 근거를 연결한 뒤 #24의 IPC 구현을 시작한다. 서비스·인터페이스 설계는 지금 진행할 수 있다. 프로파일별 CPU·메모리·IRQ·큐·시간 초과 예산을 정한다. [스케줄링 추적](https://github.com/Romanof123/JNOX/issues/21) · [IPC 작업](https://github.com/Romanof123/JNOX/issues/24)

## 커널·부팅·서비스 경계

- [ ] **BSP·릴리스 · CAP-001/002/009/014.** 펌웨어, 부팅 설정, 이미지 배치, 적재 주소와 디버그 심볼을 고정한다. 명세로 재빌드해 해시를 대조하고, 전원 인가부터 초기화·RAM 확인·타이머와 IRQ 설정·첫 작업까지 직렬 기록을 확보한다. 경합 중 스레드 대기·깨우기, 종료, CPU 친화성을 재현한다. 모델 직접 적재, 펌웨어 부팅, 실보드 결과를 구분해 기록한다.
- [ ] **커널·사용자 런타임 · CAP-004/005/018.** 확인된 단일 프로세스 시작·종료를 확장해 부모가 종료 또는 오류를 기다리고 종료 상태를 회수하는 동작과 매핑·파일 기술자·핸들 반환을 검증한다. 범위를 벗어난 세그먼트와 호환되지 않는 이미지를 거부한다. 한 프로세스에 접근 권한 오류를 유도해 다른 프로세스의 격리를 확인한다. ABI별 시스템 호출과 오류 계약을 공개하고 동적 링크 구성에는 인터프리터와 공유 객체 버전을 고정한다. [로더 설계](architecture.md)
- [ ] **커널·IPC · CAP-003.** 서로 다른 주소 공간의 클라이언트와 서버로 요청·응답, 용량 제한 알림, 공유 버퍼 소유권과 권한을 시험한다. 응답과 시간 초과·상대 종료를 경합시키고 큐 포화와 서버 재시작을 유도한다. 최종 결과가 하나인지, 자원 회수·우선순위 복원·오래된 핸들 거부가 이루어지는지 본다. 안전 채널의 유효기간·입력 상실·재무장은 별도로 판정한다. [IPC 프로파일](ipc-mechanisms.md)
- [ ] **드라이버 SDK·이름공간·격리 · CAP-004/006/017/019/020.** 장치 경로 등록과 동시 열기, 열린 핸들별 권한 집행, 재시작 시 무효화를 시험한다. 한 장치를 사용자 공간 Rust 드라이버로 구동한다. 별도 Linux 드라이버 구성에서는 원본 모듈과 펌웨어를 고정해 게이트웨이를 통해 기준 장치 동작을 재현한다. MMIO·IRQ·DMA 버퍼·리셋 소유권을 시험하고 허용 범위 밖 전송을 차단한다. 경쟁 부하에서도 제어 작업의 CPU·메모리 할당량이 보존되는지 본다.

## 사용자 서비스

- [ ] **시간 서비스·BSP · CAP-001/012.** 단조 시계, 달력 시각, 타이머 계약을 정의한다. 단조 시계의 절대 타임아웃을 기다리는 중에 달력 시각을 변경한다. 취소와 만료의 경합, 동기 상실, 허용 전력 상태별 기상을 시험한다. 원시 관측에 해상도와 불확도를 기록한다. [시스템 시간 계획](system-time-plan.md)
- [ ] **파일시스템·블록·BSP · CAP-006/007/008.** 읽기 전용 이미지와 RAM 파일시스템에서 시작해 파일과 디렉터리의 영속화 시점이 명시된 쓰기 매체를 추가한다. 경로 해석, 권한, 공간 부족, 플러시, 매체 분리와 재마운트를 시험한다. 선택한 매체에서 커밋 단계 전후로 전원을 차단해 성공 응답한 내용, 메타데이터와 복구 시간을 확인한다. [파일시스템 계획](filesystem-plan.md)
- [ ] **런타임·네트워크·SDK · CAP-005/010/011/018.** 별도 빌드한 Rust 앱, 네이티브 C 프로그램 두 개를 잇는 셸 파이프, 같은 ISA용으로 고정한 Linux CLI를 일반 권한에서 실행한다. 인자·입출력·종료 상태를 기록한다. 로컬 소켓 및 IPv4/IPv6의 TCP·UDP에서 동시 연결, 비차단 준비 알림과 역압을 시험한다. 해당 구성에서는 노드 간 요청을 끊고, 격리된 네트워크 스택 하나를 부하 중 재시작한다. [앱 인수 사례](verification-plan.md)
- [ ] **화면·주변장치 · CAP-021.** 화면을 생략한 구성도 부팅한다. 선택한 화면·입력 장치에서 정해진 입력으로 실제 표시 프레임을 바꾸고 두 식별자를 기록한다. 부하 중 창 포커스, 클라이언트 재시작, 버퍼 회수를 시험한다. 오디오와 USB를 선택한 구성에는 오디오 언더런과 USB 분리·재열거 기록을 따로 남긴다. [윈도 시스템 계획](window-system-plan.md)

## 운용·제품 출시

- [ ] **진단·도구 · CAP-013/014.** 정확한 이미지로 크기가 제한된 IRQ→스레드→서비스 추적을 해석한다. 오버플로를 유도해 유실 건수를 대조하고 추적을 끈 구성과 비용을 비교한다. 다른 프로세스의 데이터를 제외한 허용 범위의 크래시 덤프를 심볼로 해석한다. SDK·심볼·명세와 재현 명령을 패키징한다. [애플리케이션 추적](application-tracing.md)
- [ ] **보안·감시·릴리스 · CAP-015/016.** 허용되지 않은 서비스 동작을 거부하고 사용 중인 핸들의 권한을 회수한다. 부하 중 서비스 정지·재시작으로 제한 시간 안의 복구와 이전 세대 거부를 확인하고, 변조된 이미지와 금지된 하위 버전을 거부한다. 서명 업데이트를 도중에 중단하고 승인된 복구 이미지로 부팅해 실제 식별자를 확인한다. 서명 정책, 롤백 규칙, 구성품 목록과 고장 기록을 보관한다.
- [ ] **BSP·기능안전·독립 검증 · 선택한 CAP 구성.** 명시한 실물 구성에서 CPU·IRQ·DMA 간섭, RAM·스택 최대 사용량, 최장 관측 제어 응답과 출력 전이를 측정한다. 근거가 있는 분석 상한, 제품 위험원, 승인한 안전 상태 도달 시간과 대조한다. 사용 가정·잔여 위험·복구 절차·현장 업데이트 책임을 승인한다. 기능안전 승인 범위는 해당 제품 구성으로 한정한다. [안전 개념](safety-security-concept.md) · [벤치 시간 결정](safety-parameters.md)
