# J-NOX platform capabilities

[한국어](platform-capabilities.md) · English

**Planning change** `CHG-004` · source baseline `715b02f`. The table reports evidence at that revision. A later single-core run verified equal-priority FIFO yield and resumption within `CAP-001`. [Change record #18](https://github.com/Romanof123/JNOX/issues/18) · [EVD-003 FIFO verification](evidence/evd-003.en.md)

This planning baseline defines the embedded real-time OS functions J-NOX intends to offer and what a verifier would have to observe before a function can be listed as supported. A product selects a board, use case and configuration. A claim about safety, timing or compatibility applies only to the configuration and evidence named in that claim. [Product objectives and milestones](product-plan.en.md) · [Safety assumptions](safety-security-concept.en.md)

**Reading the tables.** Each `CAP` has one primary product objective and lists the current requirements that cover part of its scope. New behavior in an acceptance check needs requirements, design and verification allocation before implementation. **Plan** means the check is open. **Partial** identifies a narrower published observation. **Conditional** means the row or named option applies only to a profile that selects it. The milestones and technical owners identify who prepares the work. The verification team independently reviews the candidate and its evidence. [Requirements](requirements.en.md) · [Architecture](architecture.en.md) · [Verification plan](verification-plan.en.md) · [Trace links](../trace/links.csv)

Two M1 records establish the initial evidence. A pinned Rust kernel ELF produced the expected UART output at boot on one emulated Cortex-A72 and matched across two clean builds. A separate candidate demonstrated one timer-driven preemption and return between two threads on one emulated core. Each record identifies its candidate. Board timing, SMP, process isolation and service behavior have separate acceptance checks below. [EVD-001 boot and build](evidence/evd-001.en.md) · [EVD-002 timer preemption](evidence/evd-002.en.md)

To add an interface or close a gap in a family, open a change against the relevant CAP. Name the interface version, owner, configuration, upstream objective, affected requirements and measurable acceptance check. Allocate any missing requirement, design and verification IDs. Publish the support status with the independently verified candidate and evidence level. [Change control](lifecycle.en.md)

### What a profile costs

The extended configuration can select a runtime, filesystem, network stack, debugging facility, driver domain or peripheral independently where its dependencies allow. Multi-stack networking, cross-node services, external time synchronization, low-power modes, redundancy, dynamic linking and guest assignment each require an explicit profile decision. Record which services a safety function depends on and assess those dependencies for that product.

The minimal safety configuration pins its kernel, BSP, control tasks and required I/O and monitoring path. Record each optional service, stack, guest or peripheral in the profile manifest. Compare the enabled and disabled builds for image bytes, resident RAM, stack and pool peaks, boot time, IRQ/CPU load, and worst observed deadline margin on the named board. List the components, device DMA and shared-bus interference included in timing analysis. For an omitted component, check that its service endpoints and permissions are absent. The proposed minimal AArch64 ceilings in REQ-009 are 256 KiB of kernel code plus constants and 2 MiB of kernel RAM. Report user services, firmware, guest memory and persistent storage separately.
