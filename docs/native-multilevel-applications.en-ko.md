# Multilevel queues for independent native applications / 독립 네이티브 앱의 다단계 큐

[#308](https://github.com/Romanof123/JNOX/issues/308) · CHG-122. IMP-122 and EVD-122 reserved. Prospective contract on main `369c48e31f6679dc7376985e9b303989362f8af7`. A single CPU can prioritize an operator-designated reporting class (MLQ), or classify each program by the CPU time it consumes (MLFQ). The same private C/Rust binaries support both deployments. [Shared queue policy](../kernel/src/multilevel_policy.rs) · [Feedback accounting](../kernel/src/feedback_policy.rs) · [Linked service](../kernel/src/multilevel_service.rs)

CPU 하나에서 운영자가 보고 작업에 고정 클래스를 지정하거나(MLQ), 각 프로그램의 실제 CPU 사용량에 따라 자동으로 레벨을 바꾼다(MLFQ). 같은 C·Rust ELF의 사설 데이터와 스택을 유지한 상태로 두 설정을 비교한다.

## Packaging / 설정

Use the ordinary one-to-three-slot loader and existing SDK clock, absolute sleep, yield and exit. No new syscall. Example commands below assume the reference virt counter F=62,500,000 Hz; read and record the actual CNTFRQ. The numeric options are physical counter ticks, not milliseconds.

~~~sh
python3 tools/build_native_el0.py --out strict --policy mlq \
  --elf report.elf --class 7 --peer-elf crc.elf --peer-class 1 \
  --quantum-ticks 625000

python3 tools/build_native_el0.py --out feedback --policy mlfq \
  --elf report.elf --peer-elf crc.elf \
  --allotment-ticks 625000,1250000,2500000 --boost-ticks 6250000
~~~

For MLQ require exactly one unsigned class 0…255 per ELF in package order and one common positive quantum. For MLFQ require exactly three positive allotments, top/middle/bottom, and one positive global boost period. Every process starts at the top. Require each duration ≤ i64::MAX with checked absolute compares and checked cumulative counters. Raw Cargo inputs are JNOX_NATIVE_POLICY=mlq|mlfq, JNOX_NATIVE_CLASSES (comma-separated), existing JNOX_NATIVE_QUANTUM_TICKS, JNOX_NATIVE_ALLOTMENT_TICKS (three comma-separated), and JNOX_NATIVE_BOOST_TICKS. Reject invalid decimal fields, missing/extra entries, repeated singleton options, mixed selectors, policy options on the startup probe, and a fourth slot. Validate at CLI and raw build boundaries. Preserve filename, hash, slot order, raw values and units in package metadata. Existing cooperative, fixed, weighted, EDF and reservation selectors keep their original contracts.

MLQ는 각 ELF의 0~255 클래스와 공통 퀀텀을 받는다. MLFQ는 상·중·하 세 할당량과 전체 승격 주기를 받으며 모두 최상위에서 시작한다. 시간 인수의 단위는 물리 카운터 틱이다. CLI와 Cargo 양쪽에서 개수·범위·상충 설정을 확인하고 패키지에 입력 순서, 단위와 해시를 남긴다.

## Scheduling boundaries / 스케줄링 경계

Use Multilevel::fixed/feedback, wake, close_interval, boost and dispatch as the only selection and feedback state. Enable the existing measured charge_interval path for native use; keep the linked runtime and its own closure points intact. Wake initial slots in package order. At each dispatch snapshot the selected private ELR/SP and mapping. Sample start at the final restore path and stop at the first exception-entry sample ending that interval. Accumulate each owner's uncapped elapsed ticks once; exclude idle and the stop-to-next-start gap. An ordinary nonblocking clock call or an already elapsed sleep retains the active grant. Check user pointers in the caller's address space. Terminal slots never reenter readiness.

- MLQ chooses the largest class. Equal classes rotate FIFO on expiry or yield. A stopped runnable owner reenters the tail; every selection gets a fresh quantum. An arbitrarily busy higher class can exclude a lower class while continuously ready.
- MLFQ chooses the largest effective rank (2,1,0). All dispatches at a level consume the same remaining allotment, including short intervals ending in yield or sleep. On exhaustion demote one level; the bottom renews its own allotment. A late IRQ charges the actual owner through all crossed levels using the shared bottom-level remainder calculation. It produces one real selection at the observed sample. No synthetic intervening dispatches.
- A PPI30 sleeper wake is a scheduling boundary, matching the linked wake-and-reselect operation. Enqueue all due sleepers once, ordered by absolute target then slot, before requeuing the outgoing runnable owner. Wake preserves the sleeper's rank and remainder. A strictly higher ready rank therefore preempts; an equal newly woken peer can precede the outgoing owner, and other previously queued equals keep FIFO order. A lower wake can leave the same process running. Future sleep removes the caller; yield queues it; exit closes its interval and removes it permanently.
- Anchor boosts at positive multiples of B in aggregate measured owner service from zero, the coordinate used by multilevel_service. Idle contributes zero. Arm the earliest of owner grant expiry, due sleep, and (in MLFQ with an owner) the next cumulative boost threshold translated to wall ticks at this dispatch. With no ready owner arm only the earliest sleeper. At a coincident event charge once, admit wakes before requeue, close the outgoing interval, then boost all feedback slots including sleepers before dispatch. Boost restores top level/full allotment and preserves existing ready order. One reset after a late uninterrupted interval suffices; record the number of crossed thresholds and the next anchored multiple. Never restart the period relative to late delivery. Disable unused compares and stop explicitly on arithmetic exhaustion.

MLQ는 큰 클래스가 우선이고 동률은 FIFO다. 선택될 때마다 새 퀀텀을 받는다. MLFQ는 양보와 수면 전까지의 사용량을 합산하고, 레벨 소진 시 강등하며 최하위에서는 잔여량을 순환한다. 실제로 늦게 온 IRQ의 경과량은 당시 실행자에게 한 번만 부과한다. 기한이 된 대기자는 기한·슬롯 순서로 먼저 준비 큐에 넣고 실행자를 뒤에 넣는다. 더 높은 순위는 즉시 선점하고 동률은 이 큐 순서를 따른다. 전체 승격의 기준은 유휴와 디스패치 간격을 제외한 누적 CPU 서비스다. B의 배수를 넘으면 대기 중인 앱도 최고 레벨로 복구하고 준비 큐 순서를 유지한다.

## Reference products and first positions / 기준 앱과 최초 실행

Use one Cortex-A72, QEMU virt/GICv2, TCG, 128 MiB and default clock. At the reference F the configuration above is MLQ quantum 10 ms, MLFQ allotments 10/20/40 ms and boost every 100 ms of charged service. Use the existing CBS CRC and Rust histogram binaries built from the public SDK. Each processes 4,096-byte ramps until its first completed block after 650 ms of observed wall time, bounded by the existing block cap. Preserve their private byte counts and CRC-32 or sixteen histogram bins and their signed exits 17/29. Verify CRC independently against zlib over the actual completed bytes and every bin against 256 times completed blocks. [Source and existing input oracle](../examples/native-cbs/README.md)

For report.elf use three absolute waits, each at current SDK monotonic time +40 ms. After each wake reduce a fresh 4,096-byte ramp x[i]=(17i+3+round) mod 256, count samples ≥240 using volatile input, publish the round count (256), cumulative count (256,512,768), requested time and observed time in private writable memory, then exit 53 after round three. The application uses only SDK calls and never reads scheduler state. For the voluntary-yield control build one finite client that performs 16,384 complete 4,096-byte ramps, yields after every block, and publishes total bytes (67,108,864), count ≥240 (4,194,304) and exit 59. A yield control may use a dedicated, predeclared bounded prefix for a scored trace; retain total outcomes and explicit truncation rather than scoring lost transitions.

1. Freeze the binaries, disassemblies, package manifests, CLI, toolchain, exact counter scale, journal capacity and external acquisition before launch. Run each main report+CRC package plain then independently exception-traced, strict first, feedback second. Collect all first results including failures. Require real background progress between sleeps, each report at or after its own deadline, complete products and exact return contexts. Distinguish a wake-caused change from an expiry or boost using both pre-event compares and observed counters. A private return PC and external exception order can identify a handoff; a pre-ERET timestamp alone is only its lower bound.
2. MLQ three-slot control: CRC and histogram at class 7 followed by the reporter at class 1. Observe at least A→B→A while both high slots stay runnable, no lower selection during that overlap, and useful report work after high slots exit. Also freeze all-equal classes with package-order starts and explicit yield. Later self-reselection by a sole survivor and all-sleep idle must be recorded in their own controls.
3. MLFQ controls: run the yielding reduction with a continuous peer, and a report with a continuous peer. Identify a series of short yields that cumulatively crosses the top allotment before the next boost, a real demotion, an anchored reset, preserved sleeper accounting or reset while asleep, a higher-level wake preemption if actually present, private useful work and final exits. Record an exact tie or multi-level late charge only when naturally observed; use deterministic host inputs for charge/boost boundary arithmetic. No deliberate delay in the deployed path. With a sole reporter, verify real idle across the waits, return to its saved frame, and no boost from wall time spent idle.
4. Retain real observations with policy, cause, old/new slot, entry/start/restore stamps, prior and next compares, pending sleep targets, granted and uncapped service, per-slot cumulative service, ready order, effective levels, remaining allotments before and after charging/reset, boost coordinate, saved/restored ELR/SP and products. Report release-to-selection and measured service as observations. If a required overlap, demotion, boost, preemption or product is absent, leave that claim open. Historical linked multilevel measurements and physical-board guarantees keep their own scope.

기준 주파수에서 MLQ는 10 ms 퀀텀, MLFQ는 10/20/40 ms 할당량과 누적 서비스 100 ms마다 승격을 사용한다. 보고 앱은 40 ms 절대 대기 세 번 뒤 각각 4,096개 표본을 처리해 누적 256·512·768을 게시한다. CRC·히스토그램은 기존 사설 결과 전체를 독립 계산으로 확인한다. MLQ에서는 두 동급 상위 앱의 교대·하위 앱의 대기 및 이후 실행을, MLFQ에서는 부분 양보의 합산 강등·승격·수면 복귀를 실제 문맥과 제품으로 확인한다. 최초 일반 및 외부 추적 결과, 결손·실패를 모두 보존한다. 관측한 대기 시간과 서비스량은 해당 가상 구성의 결과이며 실물 보드의 응답 보장은 별도다.
