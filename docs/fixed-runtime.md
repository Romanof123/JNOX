# 단일 코어 고정 우선순위 런타임

한국어 · [English](fixed-runtime.en.md)

CHG-032 / IMP-030은 이슈 #69의 런타임 프로파일을 정의한다. EVD-030은 검증 결과를 기록할 대상이다. 아래 항목은 인수 기준이다.

## QEMU에서 빌드하고 실행하기

Linux 또는 WSL에서 저장소 루트를 기준으로 실행한다. 고정된 Rust 툴체인, AArch64 베어메탈 타깃과 `qemu-system-aarch64`가 필요하다. 아래 명령은 선택한 앱별로 릴리스 경로를 나눈다.

```sh
app=fixed-fifo
out="$PWD/out/$app"
(cd kernel && JNOX_BOARD=virt JNOX_PROFILE=fixed JNOX_APP="$app" CARGO_TARGET_DIR="$out" cargo +1.95.0 build --release --locked -j1)
python3 tools/qemu_boot.py --profile "$app" --runs 1 --kernel "$out/aarch64-unknown-none/release/jnox-kernel"
```

라운드로빈으로 실행하려면 `app=fixed-rr`을 사용한다. 빈 작업 테이블은 `fixed-empty`, 지연 시작 테이블은 `fixed-delayed`다. [링크할 작업 테이블](../kernel/src/fixed_apps.rs) · [스케줄러 인터페이스](../kernel/src/fixed_runtime.rs)

## 빌드와 애플리케이션 인터페이스

벤치마크 기능을 켜지 않고 `JNOX_PROFILE=fixed`를 지정한다. `JNOX_APP=fixed-fifo` 또는 `JNOX_APP=fixed-rr`로 링크할 테이블을 고른다. 추가 설정은 `fixed-empty`와 `fixed-delayed`다. 프로파일 미지정 시 기존 기본 진입점과 Cargo `--all-features` 동작을 유지한다. 명시적으로 지정한 설정이 충돌하면 빌드 설정 단계에서 거부한다. 엔트리, 순서, 우선순위, 초기 지연 또는 동순위 정책을 바꾸면 그 설정을 담은 이미지가 만들어진다. 스케줄러는 특정 태스크 이름, 부팅 순서, 출력 횟수 또는 종료 시간을 전제하지 않는다.

앱은 `Task { entry: fn(), priority: u8, delay: u64 }`를 0~4개 담은 순서 있는 테이블과 `Mode::Fifo` 또는 `Mode::RoundRobin(u64)`를 제공한다. 테이블 인덱스는 슬롯의 수명 동안 유지되는 식별자다. 두 슬롯이 같은 함수를 별도 스택에서 실행할 수 있다. 숫자가 클수록 우선순위가 높다. 초기 지연과 양수 RR 퀀텀의 단위는 물리 카운터 틱이다. 엔트리는 한 번 시작하며 일반 함수처럼 반환하면 트램펄린이 종료를 요청한다.

| Rust 호출 | AArch64 동기 호출 규약 | 효과 |
| --- | --- | --- |
| `yield_now()` | SVC #0 | 현재 태스크를 같은 우선순위 준비열의 꼬리로 옮기고 할당량을 갱신한다. |
| `sleep_ticks(u64) -> bool` | SVC #2, x0에 틱 수 전달 | 0은 양보한다. 양수면 절대 기한까지 차단한다. 성공 시 재개할 때 x0은 1이다. 상대 틱 수가 i64::MAX를 초과하거나 절대 기한 덧셈이 넘치면 x0은 0이며 자발적 상태 전이는 없다. |
| `exit() -> !` | SVC #1 | 현재 슬롯을 영구 종료한다. 호출자로 돌아가지 않는다. |

앱용 모듈은 설정과 태스크 호출을 제공한다. 플랫폼 내부는 벡터, 프레임 구성 및 복원, GIC, 카운터, 타이머와 전용 유휴 컨텍스트를 담당한다. 링크된 엔트리는 모두 같은 주소 공간의 신뢰된 EL1 코드다. 인터럽트·서비스에서 선언된 반환값을 제외한 태스크 상태를 보존한다. 사용자 모드, 접근 제어 및 안전 도메인 격리는 후속 범위다. 슬롯, 준비열, 전용 유휴 컨텍스트, 서로 분리된 정렬 스택은 정적으로 확보한다. 각 구성의 ELF 크기와 메모리 점유량, 슬롯·스택 예약량과 링크된 엔트리 주소를 기록한다. 신뢰된 엔트리는 예약된 스택 범위를 지키고 플랫폼 소유 타이머와 인터럽트 설정을 보존해야 한다. 힙 할당, 동적 생성, IPC 및 타이머 외 차단 서비스는 제공하지 않는다.

## 부팅, 선택 및 시간 처리

한 코어에서 IRQ를 마스킹하고 시작한다. 앱을 실행하기 전에 용량, 엔트리, 모드, 양수 RR 퀀텀, 유효한 카운터 주파수, 초기 지연과 RR 퀀텀이 i64::MAX 틱 이내인지, 초기 절대 기상 기한과 첫 경쟁 RR 비교값을 표현할 수 있는지, 스택·프레임이 정렬되고 분리되어 있는지 확인한다. 하나의 부팅 카운터 표본이 모든 초기 지연의 기준이다. 어느 엔트리든 IRQ를 받을 수 있기 전에 모든 프레임, 준비열, 예외 벡터, 인터럽트 컨트롤러와 타이머를 준비한다. 지연 0인 슬롯은 테이블 순서대로 준비된다. 모두 지연 상태면 가장 이른 기한을 설정하고 유휴 컨텍스트로 진입한다. 빈 테이블은 즉시 조용한 유휴 상태가 된다. 치명적 설정 오류나 예기치 않은 예외가 발생하면 IRQ를 마스킹하고 타이머를 끈 후 UART가 가능하면 제한된 길이의 진단을 남기고 정지한다. 일부만 검증한 앱을 시작하지 않는다.

1. 스케줄링 경계에서 단조 물리 카운터를 읽는다. 직전 결정 이후 경과 시간은 실제로 실행한 슬롯에만 부과한다. RR 잔여량은 단독 실행 중에도 소모되며 최솟값은 0이다. FIFO는 할당량이 없다. 한 부팅 세션에서 카운터가 순환하지 않고 절대 비교 기한을 표현할 수 있는 범위를 전제한다.
2. 기한이 지난 모든 슬롯을 절대 기한 오름차순, 동률이면 슬롯 번호순으로 각 준비열의 꼬리에 넣고 새 할당량을 준다. 그다음 원래 실행자의 자발적 요청을 적용한다. 양수 수면은 이번 표본에 지연을 더한다. 종료·수면·양보한 실행자에게 같은 경계에서 퀀텀 만료를 중복 적용하지 않는다.
3. 여전히 실행 가능한 RR 태스크의 잔여량이 0이고 동순위 준비 태스크가 있으면 새 할당량으로 꼬리에 넣는다. 그 외에 상위 우선순위가 선점하면 기존 실행자는 자신의 우선순위에서 맨 앞을 유지하고 잔여량도 보존한다. FIFO 동순위 태스크는 양보·차단·종료할 때까지 실행하며 상위 우선순위는 선점할 수 있다. 최고 우선순위 준비열의 첫 슬롯을 선택한다. 앱 태스크를 하나도 실행할 수 없을 때만 유휴 컨텍스트를 선택한다.
4. 다음 기상 기한과 동순위 경쟁자가 있는 실행자의 RR 만료 중 가장 이른 절대 기한 하나를 설정한다. 동순위 경쟁자가 없으면 퀀텀 IRQ가 없다. 경쟁 중인 RR 절대 비교값이 넘치면 기한 계산이 CompareOverflow를 반환하고 플랫폼은 치명적 오류로 정지한다. 처리할 만료가 있는 타이머를 조용히 비활성화해서는 안 된다. 뒤늦게 동순위 태스크가 준비되면 0을 포함한 실제 잔여량을 적용한다. 핸들러가 늦으면 밀린 기상을 모두 반영하고 한 번만 선택한다. 실행하지 않은 태스크의 서비스나 과거 회전을 만들어내지 않는다. 비교값 설정 중 기한이 지나면 IRQ가 대기하거나 즉시 재평가되어야 한다. 타이머 IRQ는 컨트롤러에서 확인하고 완료 처리한다. 기한이 없으면 타이머를 끈다. 모두 종료한 뒤에는 주기 IRQ, 태스크 재시작, 반복 UART 출력 없이 전용 유휴 컨텍스트가 대기한다.

### 검증용 앱과 캡처 대응

FIFO 테이블의 슬롯 순서는 A, B, HIGH이고 RR은 A, HIGH, B다. 두 설정에서 HIGH의 초기 지연은 Q/2이고 Q는 12,500,000틱이다. FIFO A가 양보하면 B는 A가 준비된 상태에서 sleep(0)을 호출한다. HIGH가 A를 선점할 때 B는 여전히 준비 상태다. HIGH 반환 뒤 A가 B보다 먼저 재개하고 반환한다. 그 뒤 B는 2Q 동안 자고 깨어나 sleep(u64::MAX)가 false인지 확인한 후 명시적으로 종료한다. RR의 퀀텀은 Q이고 HIGH는 적어도 Q/4 카운터 틱 동안 실행한다. `fixed_app_observations`는 리틀엔디언 u64 여덟 개로 구성된다. 순서대로 A·B·HIGH의 SP, A·B의 진행량, HIGH에서 본 A 진행량, B 진입 시 본 A 진행량, A 완료 직전에 본 B 진행량이다. FIFO에서는 A 최종 진행량 > HIGH에서 본 A 진행량 > 0이고 나머지 세 진행 측정값은 0이다. RR에서는 0 < HIGH에서 본 A 진행량 < B 진입 시 본 A 진행량 < A 최종 진행량이고, 0 < A 완료 직전에 본 B 진행량 < B 최종 진행량이다.

각 ELF에 대해 `python3 tools/qemu_boot.py --kernel "$elf" --profile fixed-fifo` 또는 `fixed-rr`로 실행한다. Linux에서 `FIXED_RUNTIME_CAPTURE_DIR`를 새 절대 경로로 지정하고 `--qemu ./tools/fixed_runtime_capture.py`를 추가하면 UART, 예외 추적, 앱 관측값, CPU 레지스터를 보관한다. `aarch64-linux-gnu-nm`이 필요하다. 조용한 구간 뒤 정지한 PC가 해당 ELF의 `fixed_runtime_idle` 범위에 드는지 확인하고 선점·복귀 PC를 실제 엔트리에 대응시킨다.

| 링크된 앱 | 순서대로 나온 UART 접미어 (각 줄은 FIXED 및 대문자 앱 이름으로 시작) | 추가 확인 |
| --- | --- | --- |
| FIFO | START, A START, B YIELD, A RESUME, HIGH, A DONE, B SLEEP, B DONE | B의 0틱 양보, 양수 수면, 범위 초과 수면 거부, 명시적 종료를 확인한다. |
| RR | START, A START, HIGH, B START, A DONE, B DONE | 두 동순위 태스크가 상위 슬롯의 선점과 타이머에 의한 회전을 거쳐 실행된다. |
| EMPTY | START | 앱 슬롯이 없고 첫 컨텍스트는 타이머를 끈 유휴 상태다. |
| DELAYED | START, TASK | 우선순위 1인 FIFO 슬롯 하나의 지연은 Q/2이다. 부팅 후 비교값을 설정한 유휴 상태에서 타이머 IRQ가 슬롯 0을 실행한다. 이 슬롯은 명시적으로 종료한다. |

일반 이미지는 계측 설정 없이 빌드하여 독립적으로 관측한다. 진단용 fixed 이미지에만 빌드 시 `JNOX_FIXED_TRACE=1`을 지정한다. 두 종류의 ELF 해시, 빌드 설정 및 캡처를 별도로 보관한다. 선택적 기록기는 정적 메모리에 사건 처리 직후 상태를 발생 순서대로 최대 64행 저장한다. 공간이 차면 기존 행은 유지하고 누락을 표시한다. 실행을 복원하기 전에 기록 행 수와 오버플로를 확인한다. 각 행은 일반 스케줄러 사건을 기록하며 시험에 특정한 슬롯이나 예상 순서를 내장하지 않는다. 연속 카운터 표본의 차이와 당시 실행 슬롯에서 서비스 시간을 구해 사건 수, 설정한 절대 기한 및 타이머 레지스터 실측값과 대조한다. 진단 빌드에서 관찰한 시간은 제품 지연 시간의 상한을 보장하지 않는다.

#### 바이너리 추적 형식

공개 심벌 `fixed_runtime_trace`는 C 레이아웃이며 모든 워드는 리틀엔디언 u64다. 헤더 순서는 [count, overflow, frequency, row_words]이다. count는 저장 행 수(0~64), overflow는 이후 누락된 행 수, frequency는 Hz 단위 주파수, row_words는 19다. 헤더 뒤에 64행의 공간이 있으며 앞의 count행만 읽는다. 계측된 이미지에서 `trace.bin`을 저장하고 `launch.json`에 링크된 심벌 주소와 크기를 기록한다. 추가 설정은 각각 `--profile fixed-empty` 또는 `--profile fixed-delayed`로 캡처한다.

| 워드 인덱스(0부터) | 저장 순서 및 의미 |
| --- | --- |
| 0~4 | 사건 종류(0 부팅, 1 타이머 IRQ, 2 SVC), 원인(원시 INTID 또는 SVC 즉시값, 부팅은 u64::MAX), 카운터 표본, 직전 소유자, 선택 소유자. 유휴 번호는 4, 부팅 직전 소유자는 u64::MAX다. |
| 5~10 | 진입한 예외 프레임 주소, 저장된 ELR, 중단 SP, 선택된 프레임 주소, 선택 ELR, 선택 SP. SP는 프레임 주소에 프레임 크기를 더한 값이다. 프레임이 없으면 해당 세 필드는 0이다. |
| 11~14 | 수면 인자, 수면 결과(1 수락, 0 거부), 다음 비교값 유효 플래그, 의도한 절대 비교값. 수면 이외 사건에서는 수면 두 필드가 0이다. 무효 비교값은 0이다. |
| 15~18 | 설정 후 CNTP_CTL, 설정 후 CNTP_CVAL, IRQ 처리 전 CNTP_CTL, 이 사건 경과분까지 반영한 직전 소유자의 누적 서비스 시간. IRQ 전 제어값 또는 누적 서비스가 없으면 해당 필드에 u64::MAX를 쓴다. 비활성 타이머의 CVAL에는 과거 값이 남을 수 있으므로 CTL과 유효 플래그를 함께 판독한다. |

시간순으로 i행에서 선택된 소유자가 i+1행 표본까지 실행된다. 이 소유자가 다음 행의 직전 소유자와 같은지 확인하고 앱 슬롯별로 표본 차이를 누적해 18번 워드의 유효한 값과 비교한다. ELF와 ELR/SP를 대조해 최초 진입, 중단, 재개 및 유휴 상태를 식별한다.

빈 구성의 작업 관측값 여덟 개는 모두 0이다. 지연 시작 구성은 슬롯 0의 정렬된 스택 포인터를 첫 번째 값에 기록하며 나머지 일곱 개는 0이다.
