# AArch64 응용 이식 파일럿 · Telemetry Monitor

[English](telemetry-migration-pilot.en.md) · CHG-084 · 승인 계획

제품 목표는 지정된 안전 응용의 필수 동작·장치 접근·고장 반응을 유지하면서 기반 운영체제를 교체하는 것이다. 첫 개발 파일럿은 프로젝트가 작성한 C 소스 `examples/portability/telemetry_monitor.c`로 파일을 읽어 요약 한 줄을 출력하는 프로세스다. 같은 파일을 각 운영체제의 SDK·libc 시작 코드로 별도 컴파일한다. 현재 실제 상용 응용 소스, 원본 시스템 SDK, 실행 가능한 원본 이미지와 장치는 확보되지 않았다. 먼저 지정한 호스트 기준선을 기록하고 통합 담당자가 입력을 확보하면 해당 환경에서도 비교한다. [제품 기획](product-plan.md) · [플랫폼 점검표](platform-checklist.md)

## 프로세스 계약

인수로 경로 하나를 받는다. `open`(`O_RDONLY`)·`read`·`close`로 파일 바이트를 읽고 `write`로 결과를 쓴다. 한 레코드는 ASCII 십진 숫자 하나 이상과 LF로 구성되며 마지막 LF도 필수다. 범위는 0~65535이고 앞자리 0을 허용한다. 부호·공백·빈 줄·CR·NUL·숫자 외 바이트·마지막 LF 누락은 오류다. 짧은 읽기 경계에 걸쳐 파싱하고 부호 없는 64비트 건수와 합의 범위를 검사한다. 중단된 open/read/write는 재시도하고, 부분 전송이면 옮긴 바이트 다음부터 계속한다. 연 입력은 한 번만 닫는다. 입력 처리와 닫기에 성공한 뒤 요약을 출력한다.

| 종료값 | 표준 스트림에 쓸 수 있을 때의 관측 |
| --- | --- |
| 0 | stdout은 최소 자릿수의 부호 없는 십진수로 `samples=N min=L max=H sum=S\n`, stderr는 비어 있다. |
| 2 | 인수 개수 오류. stderr `usage: telemetry_monitor PATH\n` |
| 3 | 입력 파일이 0바이트. stderr `empty input\n` |
| 4 | 레코드 형식 또는 값 범위 오류. stderr `invalid sample\n` |
| 5 | 파일 부재를 포함한 입력 열기·읽기·닫기 실패. stderr `input error\n` |
| 6 | 건수 또는 합이 uint64 범위를 초과. stderr `summary overflow\n` |
| 7 | 요약 쓰기 실패. stderr `output error\n`. 이미 쓴 stdout 앞부분은 남을 수 있다. |

여기서 `\n`은 바이트 0A 하나다. 종료값 2~6이면 stdout은 비어 있다. `0\n0007\n65535\n`의 결과는 `samples=3 min=0 max=65535 sum=65542\n`이다. 빈 파일(3), LF 하나(4), LF 없는 `7`(4), `65536\n`(4), 없는 경로(5)를 구분한다. 오버플로는 산술 경계 시험으로도 확인할 수 있으며 실제 프로세스에서 관측한 범위를 기록한다.

## 단계별 근거

| 단계와 책임 | 다음 단계로 넘어갈 때 필요한 관측 |
| --- | --- |
| 1 · 응용·독립 검증 | 소스·입력 해시, 명령행, OS별 실행 파일과 컴파일러·시스루트를 고정한다. 명시한 호스트에서 읽기 경계에 걸치는 레코드 등 동일한 입력 모음을 실행한다. 별도 검증자가 예상 바이트를 계산하고 각 사례의 stdout·stderr 원본 및 부모가 회수한 종료값을 남긴다. 사용 권한이 있는 원본 SDK와 타깃을 확보하면 같은 관측을 추가한다. 각 결과의 환경, 미지원 사례와 실패도 기록한다. |
| 2 · 커널·IPC·파일 서비스·SDK | #21에서 해당 스케줄링 승인을 완료한 뒤 #24의 IPC 개발을 시작한다. 공개 C 헤더·libc·시작 코드로 별도 정적 AArch64 ELF를 만들고 링크 맵을 보관한다. 격리된 EL0 주소 공간에서 argv와 읽기 전용 루트 이미지의 허용 경로를 주어 실행한다. 디스크립터는 권한 있는 IPC로 사용자 공간 이름·파일 서비스에 연결한다. 진입·권한, 읽기 전용 열기, EOF까지 읽기, 출력 쓰기, 닫기, 종료와 부모의 회수를 추적한다. 실패 시 반환값·해당 errno(없는 파일은 −1/ENOENT)를 관측하고 1단계와 프로세스 출력을 대조한다. 반복 실행 후 매핑·디스크립터·미결 요청 회수를 확인한다. [IPC 프로파일](ipc-mechanisms.md) · [파일시스템 계획](filesystem-plan.md) |
| 3 · 서비스·드라이버·운영 | 선정 장치에서 실제 데이터 소스를 이름 있는 자원 서비스로 이식한다. 네이티브 Rust 드라이버 또는 격리된 Linux 드라이버 도메인을 선택하고 IRQ·MMIO·DMA·리셋 권한을 명시한다. 경합 부하 중 서비스 상실, 오래된 핸들 거부, 제한 시간 내 완료·회수, 재시작과 새 열기를 확인한다. 용량이 정해진 프로세스·IPC·장치 추적에 시각·유실 건수·계측 비용을 남긴다. #8에서 네이티브 C 셸 파이프라인, 네이티브 Rust SDK 응용, 선정 POSIX API, 동일 ISA의 기존 Linux ELF 실행을 각각 검증한다. [플랫폼 점검표](platform-checklist.md) · [POSIX 프로파일](posix-profile.md) |
| 4 · 제품 담당·BSP·기능안전 | 구매 전 보드·예산·담당자를 승인한다. 제품 적격성 평가에는 실제 응용과 원본 실행 기준, 정확한 보드·리비전, 입력 장치·액추에이터, 운용 조건·안전 매뉴얼이 필요하다. 별도로 선정한 제어 경로는 HARA로 안전 상태·ASIL·고장허용시간·단조 시계 기준 기한·시간 예산을 도출한다. 지정 실기기에서 독립 시간 기준으로 입력부터 출력, 부하·IRQ·DMA 간섭, 상실·지연·재시작과 액추에이터의 물리 안전상태 진입을 관측한다. 실측 최댓값과 근거 있는 상한을 예산·마진과 대조한다. 펌웨어·서명 이미지·툴체인·복구 절차, 잔여 위험·독립 평가·아이템 통합 승인을 기록한다. [시계 계획](system-time-plan.md) · [기능안전 판단 ADR-001](safety-parameters.md) |

각 단계의 상태는 OS·구성·장치별로 기록한다. 첫 파일 파일럿은 C 호출 네 개와 프로세스 시작을 다룬다. 기존 제품을 대체하려면 해당 커널·서비스·장치·운영·물리 안전 단계까지 완료해야 한다. CHG-084는 REQ-014/020과 DES-005 / VER-014/020을 추적하며, 전체 SDK·API 승인 사례는 #8에서 관리한다. [검증 계획](verification-plan.md)
