# Scheduling policies and release criteria

[한국어](scheduling-policies.md) · English

J-NOX profiles select how a CPU chooses its next thread, which events may preempt it, where it may run, and how much CPU time it may use. For example, a control profile can pin threads to one CPU, assign priorities by period, use FIFO within a priority, and apply a ceiling to a shared mutex. An extended profile can schedule weighted service threads inside a CPU reservation. Each combination has its own configuration and verification record.

`CHG-005` tracks this product scope through `OBJ-004 → REQ-023 → DES-012 → VER-023`. Timing and isolation also require `REQ-002 → DES-003 → VER-002`, and thread operations require `REQ-005 → DES-003 → VER-005`. Each `POL` ID identifies a family. Results identify the particular variant, layer, processor count and configuration tested. ## What the first implementation exercises

| Evidence scope | J-NOX case | What the verifier can establish |
| --- | --- | --- |
| Recorded context switches | `POL-002`, AArch64, one emulated CPU | A timer made a higher-priority thread runnable and LOW resumed at its interrupted PC. Two equal-priority threads ran on separate stacks in FIFO order and yielded to each other. The captures retain exception returns for the actual switches. [EVD-002](evidence/evd-002.en.md) · [EVD-003](evidence/evd-003.en.md) |
| Verified context switches | `IMP-004`, fixed-priority round robin (RR) | Three timer expiries rotated non-yielding peers A → B → A → B. The interrupt trace and linked instructions identify each entry and resumption. [EVD-004](evidence/evd-004.en.md) · [M1 RR contract](m1-rr.en.md) |
| Verified context switches | IMP-005, POL-005 EDF | A timer released a later-arriving task with lower static priority and an earlier absolute deadline. The trace shows its dispatch, exit and the original runner’s resumption. [EVD-005](evidence/evd-005.en.md) |
| Verified selection and accounting | `IMP-004`, bounded primitives from POL-001 through POL-018 | Controlled ready sets, clocks, charges, draws, CPU masks and operating-point models passed in one guest. Each result covers its stated decision or state transition. [EVD-004](evidence/evd-004.en.md) |
| Integrated profile release | Each enabled variant | Run actual blocking, wakeup, expiry, switch and exit paths that apply to that profile. Record target traces. Physical timing, analysis and product safety review have their own milestones. |

The candidate hard-CBS backend assumes prior admission, integer ticks, deadline equal to period and at most one outstanding job per server. The stride backend assigns equal service quanta. MLFQ charges a task across yields in three levels and applies a caller-triggered boost. The lottery backend takes a draw as input. Weighted virtual runtime and EEVDF rank supplied snapshots of already placed requests. Waking, moving and preempting real threads under those policies belong to integration. [Temporal policies](../kernel/src/temporal_policy.rs) · [Reservation and stride](../kernel/src/service_policy.rs) · [Feedback and lottery](../kernel/src/feedback_policy.rs) · [Fair selection](../kernel/src/fair_policy.rs)

The milestone in each row is the intended integration or release stage. M1 covers single-core mechanisms, M2 adds service demand and temporal isolation, M3 covers SMP and board measurements, and M4 covers extended general-purpose services. M5 assesses the frozen safety configuration. M6 repeats the relevant cases on additional ports. An M1 candidate may exercise part of an M4 policy before that profile can run applications. ## Single-core dispatch and real-time policies

| ID and policy | Dispatch rule and intended profile | Release case |
| --- | --- | --- |
| POL-001 · FCFS, cooperative scheduling and event loop | First-come, first-served (FCFS) selects the oldest ready arrival. A cooperative thread runs until it yields, blocks or exits. A run-to-completion event loop dispatches one handler per event. M1 minimal or service profile. Candidate covers FCFS selection. | Give the earliest arrival the highest numerical thread ID. With another job arriving mid-run, check that the first job retains the CPU until the specified dispatch point. In the event loop, enqueue an event from a handler and verify dispatch after handler return. Bound handler time and queue depth. |
| POL-002 · Fixed priority (FP), FIFO and RR | Select the highest ready priority. Nonpreemptive FP waits for a dispatch point. Preemptive FP can interrupt a lower-priority runner. Peers follow FIFO, or rotate after a configured quantum under RR. One priority level gives ordinary RR. M1 kernel, M3 board. | Release HIGH while LOW computes and distinguish immediate preemption from deferred dispatch. With two peers, test arrival, voluntary yield, preemption by HIGH, quantum expiry and exit. Record queue position and the declared residual quantum on resumption. See the recorded and candidate scopes above. |
| POL-003 · SJF, SRTF and HRRN | Shortest job first (SJF) ranks by estimated service at a nonpreemptive dispatch. Shortest remaining time first (SRTF) reconsiders remaining work on arrival. Highest response ratio next (HRRN) maximizes `(wait + service) / service` at a nonpreemptive dispatch. M1 ranking candidate, M4 batch services. | With a running job having four units left and a new two-unit job, SRTF switches and SJF retains the runner. In HRRN a five-unit job waiting ten units beats a fresh one-unit job. Exercise equal scores, invalid estimates and an underestimated long job. |
| POL-004 · Rate monotonic (RM) and deadline monotonic (DM) | Assign fixed priorities by shortest period for RM, shortest relative deadline for DM. M1 ranking candidate, M3 periodic control. | Release A and B together with (period, relative deadline) of (10, 9) and (12, 4). RM chooses A and DM chooses B. Exercise later releases, missed deadlines and response-time analysis including blocking, jitter, IRQ and dispatch overhead for the admitted task set. |
| POL-005 · EDF and LLF | Earliest deadline first (EDF) chooses the earliest absolute job deadline. Least laxity first (LLF) minimizes `absolute deadline − now − remaining execution`. M1 ranking candidate, M3 bounded real-time profile. | At time zero, use (deadline, remaining work) of (8, 1) and (10, 8). EDF chooses the first and LLF the second. During execution test a new earlier deadline, a change in least laxity, ties and a negative laxity. Specify reevaluation granularity and bound switch frequency. |
| POL-006 · Cyclic executive, static table and time partitions | A cyclic executive invokes predefined work in a repeating frame. A time-partition dispatcher assigns windows in a major frame to domains, which may have their own inner policy. M1 static window selection candidate, M2 integration, M3 board. | Test the tick before a boundary, the boundary itself, uncovered idle time and wrap into the next major frame. Reject overlapping/out-of-frame slots. Overrun a job and observe the declared action and the next domain's actual entry. |
| POL-007 · Polling, deferrable and sporadic servers | A polling server can forfeit unused capacity at an empty poll. A deferrable server keeps unused budget within its period. A sporadic server schedules replenishments tied to consumption under its specified rules. M1 candidate computes polling and deferrable service grants and sporadic grants with a bounded replenishment queue. M2 connects real requests and timers. M3 measures control interference on hardware. | Submit requests just after an empty poll and on both sides of a period boundary. Compare service times and remaining capacity for each variant. For a sporadic server, check each replenishment amount and time, the bound on pending replenishments and the behavior at that bound. |
| POL-008 · CPU reservations and EDF with a constant bandwidth server (CBS) | A periodic capped reservation charges execution and restores budget at a period boundary. Hard CBS schedules eligible servers by their scheduling deadlines, throttles on depletion and controls how budget and deadlines renew. M1 candidates cover accounting and constrained hard-CBS/EDF decisions. M2 integration, M3 board. | Spend the final unit, attempt another dispatch, and check exact replenishment. For CBS also exercise early/late wakeup, deadline updates, and earliest eligible server under competing demand. For profile release, reject inadmissible demand and show that an overrunning client cannot consume its neighbor's allocation. |

The real-time references define assumptions for analysis and server behavior. Each J-NOX release case also accounts for its implemented timer, dispatch overhead and blocking model. [Liu and Layland](https://web.cs.wpi.edu/~cs502/f07/Papers/Liu%20%26%20Layland%2C%20Real-time%20Scheduling.pdf) · [Sporadic server design](https://sei.cmu.edu/library/implementing-sporadic-servers-in-ada/) · [EDF and CBS](https://docs.kernel.org/scheduler/sched-deadline.html)

## General-purpose and proportional-share policies

| ID and policy | Service rule and intended profile | Release case |
| --- | --- | --- |
| POL-009 · Multilevel queue (MLQ) and multilevel feedback queue (MLFQ) | MLQ assigns jobs to fixed classes and declares the rule between queues. MLFQ moves jobs between levels based on consumed service and its boost rule. M1 candidate covers bounded MLFQ accounting, M4 extended services. | For MLQ, saturate the highest class and check the documented lower-class service. For MLFQ, consume one allotment across several early yields, observe demotion, then check boost and the next dispatch amid a CPU-bound and an interactive peer. |
| POL-010 · Lottery and stride | Lottery assigns disjoint ticket intervals to runnable threads and maps a draw to its owner. Stride chooses the least pass value and advances it according to weight and service. M1 ticket-selection and stride-accounting candidates, M4 extended services. | Check the first and last draw of every interval and reject out-of-range draws. Verify the released random selection path and share distribution across independent seeds. For stride, check a fixed ratio under load, unequal service charges, late joining and safe pass normalization. |
| POL-011 · CFS-style virtual runtime | Charge actual execution inversely to weight and choose the least virtual runtime. M1 candidate covers ranking/accounting, M4 extended services. | Run two continuously ready threads at weights 1 and 2, verify each charge against the specified arithmetic, then check the 1:2 CPU share within the declared window and tolerance. Sleep and wake one thread and check its initial position and service lag. |
| POL-012 · Earliest eligible virtual deadline first (EEVDF) | Eligibility reflects service owed relative to fair share. Among eligible threads, select the earliest virtual deadline for a requested service slice. M1 candidate covers ready-state eligibility and ranking, M4 extended services. | Give an ineligible thread the earliest virtual deadline and check that an eligible peer wins. Change eligibility and requested slice, then compare the choice against hand calculations. Under live sleep/wakeup and changing weights, verify bounded service error and measured response distributions. |

Weighted service and virtual deadlines describe relative CPU access. A hard application deadline needs a separate real-time contract and admission analysis. [Waldspurger on lottery and stride](https://dspace.mit.edu/entities/publication/3105629e-350a-46b1-9009-e0ad3dfcce6a) · [Virtual-runtime design](https://docs.kernel.org/scheduler/sched-design-CFS.html) · [EEVDF eligibility](https://docs.kernel.org/scheduler/sched-eevdf.html)

## Placement, synchronization, composition and extensions

| ID and mechanism | Role and intended profile | Release case |
| --- | --- | --- |
| POL-013 · Partitioned, global and clustered SMP | Fix tasks to CPUs, let them compete across all permitted CPUs, or limit competition to one cluster. Affinity masks restrict placement and migration. M1 candidate matches a snapshot of up to 32 task IDs to at most eight modeled CPUs, reassigning matches along an augmenting path when masks conflict. M3 covers live SMP dispatch, migration and interference. | Wake jobs simultaneously on two CPUs, migrate an eligible job while contended, and pin a peer. Trace each thread on at most one CPU at a time, legal placement and single accounting across migration. For a clustered profile try to cross its boundary. Measure migration and shared-cache interference. |
| POL-014 · Priority inheritance and priority ceiling | Inheritance propagates a blocked waiter's effective priority to the lock owner. A ceiling protocol uses a declared ceiling per resource. Pin the variant, e.g. immediate ceiling, and the maximum nesting depth. M1 candidate computes effective priorities from wait-to-owner edges and ceilings on held locks, propagates inheritance transitively and rejects cycles. Actual mutex wait, wake and unlock paths are M1 integration work. M3 quantifies blocking on the board. | Block HIGH on a lock held by LOW while MEDIUM is runnable. Observe donation, chained inheritance and restoration on timeout/unlock. With immediate ceiling, check the boost at acquisition before HIGH blocks, nested release and rejection of an invalid configuration. |
| POL-015 · Mixed criticality and adaptive mixed criticality (AMC) | Distinct criticality modes specify execution budgets and which jobs may continue after an overrun. M1 candidate grants execution under a two-level LO/HI budget model, moves from LO to HI on the specified overrun, and permits an approved reset at quiescence. M3 integrates actual task execution and timer enforcement. M5 reviews the system-level response. | Run a high-criticality job to its lower-mode budget and across that boundary. Check the transition, treatment of lower-criticality work, high-mode deadlines and the declared restart or return conditions. Verify the transition interval under maximum carry-in work. |
| POL-016 · Hierarchical scheduling | A parent allocates time to groups or domains. A child policy selects among eligible threads inside its parent's allocation. M1 candidate limits each grant by the budgets of both a group and its child and accounts at both levels. M2 enforces isolation during execution. M4 integrates nested service groups. | Saturate two children and exhaust their parent first. Check that neither runs until replenishment and that a sibling group receives its allocation. Test nested wakeups, empty groups and single charging at each applicable level. Bound group count and depth. |
| POL-017 · Energy- and deadline-aware placement | Compare the board's eligible cores, operating frequencies and idle states using measured execution capacity, power and wake latency. Permit choices that meet the profile's deadline margin. M1 candidate chooses the lowest modeled energy among feasible options from a supplied operating-point table. M3 calibrates the table and measures physical transitions. M4 integrates the optional power profile. | Repeat one workload at allowed operating points. Record energy, misses, wake latency and response-time margin under thermal throttling and shared load. Exercise the documented fallback when the model or required capacity is unavailable. |
| POL-018 · Extensible scheduling | An optional extended-profile interface may supply a bounded policy for a delegated workload. The kernel retains authority over CPU masks, reservations and the fallback policy. M1 candidate validates proposed choices from a compiled-in policy and selects a fallback when required. Its input is data. An optional policy runtime with execution limits and progress monitoring requires a separate M4 prototype and adoption decision. | Exercise valid proposals, out-of-mask choices, stale thread IDs, excessive computation and a policy that stops making progress. Check detection, fallback within the configured limit, and continued service of independent reserved work. |

The cited mechanisms supply design references. Compatibility with another scheduler interface requires its own versioned contract and tests. [Priority protocols](https://research.ibm.com/publications/priority-inheritance-protocols-an-approach-to-real-time-synchronization) · [AMC analysis](https://www.cs.york.ac.uk/rts/publications/Baruah2011a.html) · [Energy model and placement](https://docs.kernel.org/scheduler/sched-energy.html) · [Extensible scheduling](https://docs.kernel.org/scheduler/sched-ext.html)

## Resource cost, time and safety qualification

- **Minimal single-core build.** The manifest names the enabled policies, preemption points, tie-breaker, IRQ attribution and maximum thread, queue and timer counts. Compare image bytes, static RAM, stack high-water marks and worst observed dispatch/charge time with and without each option. Include timer frequency, resolution and arithmetic limits. [Footprint requirements](requirements.en.md)
- **Extended and SMP builds.** Report per-CPU queues, migration/IPI cost, per-thread accounting, group depth, shared locks, trace overhead and idle-state wake costs for the enabled combination. Test full queues, simultaneous releases, repeated blocking, late or duplicate timer events and arithmetic near limits. Retain the task set, expected result, build and raw observations. [Platform profiles](platform-capabilities.en.md)
- **Tickless operation.** The RR bench programs one-shot interrupts for the initial release and peer quantum expiries. The planned tickless profile must also schedule replenishments and partition boundaries. Use the same policy and workload to compare periodic and tickless operation. Check insertion of an earlier event, cancellation, simultaneous expiries, long idle and wakeup. Record timer resolution, interrupt load and the longest observed delivery delay.
- **Safety candidate.** For an intended ASIL D safety goal, freeze the exact policy composition, task periods and deadlines, execution bounds, blocking, IRQ and shared-resource interference, overload action and hardware. Validate the analysis against board behavior under admissible worst-case load and induced overruns. Record maximum observed times and justified analytical bounds separately. M5 independent assessment applies to the specified use case, build and board. [Safety concept](safety-security-concept.en.md) · [Verification and evidence](verification-plan.en.md)
