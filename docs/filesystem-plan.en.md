## Current boundary

On AArch64 QEMU, separately packaged native `cat` and `wc` read a packaged file and exchange bytes over a pipe. The two inputs produced 2 and 76 lines. The Pi 4 FAT package supplies a kernel to firmware. EVD-050 covers a control workload and host capture. Writable mounts, namespace routing, block-backed cold reboot and interrupted-write recovery each require separate evidence. [Guest file and pipe evidence](https://github.com/Romanof123/JNOX/issues/379) · [Filesystem delivery](https://github.com/Romanof123/JNOX/issues/459)

## First usable service

1. Package two static C programs and a sample text file in a deterministic, read-only image for /. Record offsets, lengths and hashes. Reject overlapping entries, truncation, duplicates, unsupported types and names escaping the root before publication. No block driver is needed for this milestone.
2. A user-space namespace service routes absolute paths to the longest matching registered mount component. The image manager serves / and a RAM manager serves /tmp. Resolve relative paths against the caller's directory capability. Define dot, parent traversal and mount boundaries. Initially implement regular files and directories. Reject unsupported links, special files and mount operations explicitly. Restrict mount registration to a supervisor. Image writes return EROFS. RAM contents disappear on restart.
3. Freeze finite limits per profile for path/component bytes, depth, mounts, open descriptions and descriptors, RAM nodes/bytes, directory entries, queued requests, per-request transfer bytes and outstanding block operations. Publish limits in the SDK and startup manifest. Reserve buffers in advance and return ENAMETOOLONG, EMFILE/ENFILE or ENOSPC at the relevant limit. Storage waits must have a cancellation/timeout policy and cannot hold a kernel scheduling lock.
4. Map open/openat, read, write, close, stat, mkdir, unlink and same-mount rename through bounded IPC. A process descriptor references an open file description containing access mode, offset and backend identity. dup shares that offset, independent opens have separate offsets, close drops one reference and final close releases the object. Unlink removes the name while an open file remains usable. Process exit releases all descriptors. Define child inheritance and close-on-exec explicitly. Never enlarge access rights through dup, transfer, relative lookup or adoption after service restart. Reject stale handles using generations. Specify partial writes, EOF, rejection of writes through read-only opens, atomic same-mount name replacement and EXDEV across mounts.
5. Run headlessly as a target process. First read the image file, then create/write/reopen it under /tmp, exercise full quotas and descriptor reuse, and demonstrate the two external binaries in cat sample.txt | wc -l, including EOF after all writers close. Record source/image/target/SDK hashes, raw serial output, per-operation results and an independent content check. A host path or serial line printed by firmware cannot satisfy this case.

## Optional persistent storage

Select a medium before freezing the format. For a qualified managed block device, start with a dedicated data partition and a journaled filesystem such as ext4 through a maintained implementation. This enables host-side inspection and a familiar recovery toolchain. Protect the firmware partition from writes. For raw NOR/NAND, choose a flash-aware backend only after documenting erase geometry, bad-block/ECC ownership, wear and endurance. A network filesystem is a later mount with its own availability contract.

The namespace and filesystem own names, rights and recovery. A separate block service exposes bounded reads, writes, capacity, logical block size, completion and explicit cache flush. Plan a native Rust device backend first. An upstream-source backend can later implement the same interface in a J-NOX service once its required APIs and device operations are verified. Give each writable volume one owner and bound grants, request sizes, DMA mappings, timeouts and restart generations.

For durable same-directory replacement, write a temporary file in the destination directory, handle short writes, fsync its descriptor, rename over the destination, then fsync the parent directory. Propagate writeback, flush and directory-sync errors to the caller. File sync covers file contents and required metadata. Directory sync covers the new name binding. For a future cross-directory rename, sync both directories. Atomic namespace publication and durable persistence are distinct promises. Declare durable replacement unsupported for a backend lacking an effective flush or directory-sync contract. Formatting or recovery must never silently erase the last known volume.

## Acceptance and decisions

Use a disposable model disk to exercise orderly restart, server death, full storage, malformed images and interruption around each write/sync/rename boundary. After remount record the actual directory state, content generation/checksum and recovery result. Before final directory sync declare the allowed outcomes for the selected backend; after acknowledged final sync require the new complete payload. Corruption, mixed contents or silent loss of acknowledged final state fails. Model results establish software protocol behavior. For a physical persistence claim use the specified board, storage part, firmware, cache configuration and filesystem options. Cut actual storage power at recorded boundaries, remount on a fresh boot, verify independently and retain every attempt. Record recovery time, write amplification and interference with the real-time workload. Device/controller behavior sets the scope of the claim.

The product owner must choose required first applications, writable paths and capacity, medium and board, persistence after reset versus sudden power loss, supported POSIX calls, ownership/permissions, maximum acceptable loss and recovery time, and the required device isolation. The read-only image and /tmp milestone can proceed while these persistence decisions remain open.
