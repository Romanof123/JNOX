# 개발 수명주기와 변경관리

한국어 · [English](lifecycle.en.md)

J-NOX 문서는 제품 기획, 안전·보안 분석, 시스템 요구, 설계, 구현 기록, 검증 명세, 시험 증거와 출시 기준선을 각 단계의 책임 아래 관리한다. GitHub 이슈는 진행을 추적한다. 의사결정과 승인 근거는 이슈 번호로 연결한 버전 관리 문서에 남긴다.

문서·이슈·작업 양식은 한국어와 영어로 함께 관리한다. 담당 팀은 같은 변경에서 두 언어판을 갱신하고, 기준선을 승인할 때 양쪽의 추적 ID, 합격 기준, 변경 범위와 승인 상태가 일치하는지 확인한다.

## 팀과 인계

| 역할 | 책임 | 인계물 |
| --- | --- | --- |
| PM | 범위·일정·팀 간 의존성·장애 요소·승인 상태를 관리한다. 변경 요청을 시스템팀으로 전달하고 제품 책임자와 의사결정을 조율한다. | 기준선 상태, 배정 이력, 승인과 열린 의사결정 목록 |
| 시스템팀 | 제품 기획, 요구사항, 인터페이스, 아키텍처와 변경 영향을 관리한다. 보안 담당과 TARA를 조율하고 기능안전팀과 함께 안전 요구를 각 구성요소에 할당한다. | 제품 정의, 요구 ID, 인터페이스 계약, 시스템 설계 및 검증 요구 |
| 기능안전팀 | 안전 계획과 HARA를 주관하고 벤치 시험 입력값과 합격 한계를 결정한다. 시스템·통합팀과 제품 위험별 안전 상태, FTTI와 고장 반응 예산을 도출한다. 제품 출시를 안전 관점에서 권고하며 근거가 부족하면 권고를 보류한다. | 안전 목표, 적용 가정, 안전값 결정 기록, 시간 예산·여유분의 근거, 미해결 사항과 출시 권고 상태 |
| 개별 개발팀 | 승인받은 모듈 설계와 인터페이스를 바탕으로 분리 브랜치에서 구현한다. 단위 시험과 변경 근거를 제출한다. | 코드·변경 이슈, 단위 시험, 구현 ID, 알려진 제약 |
| 통합팀 | 커널·BSP·서비스·Linux 도메인 구성을 조합한다. 계약 위반과 구성을 확인하고 정확한 검증 후보를 동결한다. | 버전이 고정된 이미지·설정·도구, 재빌드 절차, SHA-256과 통합 결과 |
| 검증팀 | 매 검증 회차 새 검증자가 독립 환경에서 요구에 따라 시험·판정한다. 개발자 구현 이력과 개발·통합팀의 판정·로그는 독립 검증팀의 초기 판정과 원본 로그를 고정한 뒤 공개한다. | 자체 판정, 환경·절차·원본 로그, 새로 관찰한 문제, 커버리지·구조 검토 기록 |
| 배포팀 | 승인된 산출물과 제출 해시가 일치하는지 확인해 패키징·서명·배포·복구 검증을 수행한다. | 서명된 패키지, 릴리스 구성, SBOM·변경 목록, 배포·복구 증거 |

기능안전팀이 벤치 기준값을 동결하면 개발·통합팀은 그 범위에서 작업을 시작할 수 있다. 실제 제품값은 기능안전팀이 근거를 제출하고 독립 검토를 거친 뒤, 해당 아이템의 제품 통합 승인권자(개발 협약에 따라 OEM 또는 위임된 주체)가 적용 범위·버전·승인 결정을 기록할 때 확정한다. PM은 결정과 미해결 사항을 추적한다. [첫 벤치 결정 ADR-001](safety-parameters.md) · [ISO 26262 기능안전 관리](https://www.iso.org/standard/68384.html)

새 검증자는 해당 변경의 설계·구현·통합에 참여하지 않고, 이전 작업 세션을 이어받지 않는다. 첫 인계에는 승인된 요구·공개 인터페이스·시험 절차와 입력·기대치·빌드 식별자만 포함한다. 블랙박스 판정과 로그를 고정한 뒤 필요한 소스 검토·정적 분석·커버리지·안전 분석을 수행한다. 동일 회차 재현과 다음 검증 회차를 구분해 기록한다. 에이전트 검증은 이 방식의 실행 수단이며, 제품 안전 심사의 독립성과 책임은 승인된 조직과 담당자가 검토한다.

## 추적 기록의 규칙

여러 팀이 담당 모듈을 동시에 작성할 수 있다. PM은 통합한 소스 커밋을 고정하고 공유 호스트에서 빌드, QEMU 시험, 검토를 차례로 배정한다. 검증자는 합격 기준과 후보 해시를 받아 개발팀의 판정과 독립적으로 관측한다. 초기 상태를 공유해도 되는 시험은 QEMU 한 대에서 실행하며 사례별 입력·출력·자원 정리 결과를 기록한다. 독립적인 초기 상태나 복구 동작이 합격 조건인 시험에는 새 부팅을 배정한다.

| 기록 | ID와 위치 | 관계 |
| --- | --- | --- |
| 제품 기획 목표 | `OBJ` · [제품 기획](product-plan.md) | 위험, 위협 및 요구사항의 출발점 |
| 안전·보안 개념 | `HAZ`, `THR`, `ASM` · [개념 문서](safety-security-concept.md) | 보호 대상 및 적용 가정을 기록하고 파생 요구를 연결 |
| 요구사항 | `REQ` · [시스템 요구사항](requirements.md) | 상위 근거, 하위 설계와 합격 판정을 연결 |
| 설계·결정·구현 | `DES`, `ADR`, `IMP` · [아키텍처](architecture.md), 이후 모듈 설계·결정 기록 및 변경 PR | 설계 계약과 변경 이유, 구현 위치·버전을 연결 |
| 검증·결과 | `VER`, `EVD` · [검증 계획](verification-plan.md), 이후 시험 명세와 버전이 고정된 증거 | 요구와 실제 시험 대상, 환경·판정을 연결 |
| 변경·출시 | `CHG`, `REL` · 변경 이슈와 기준선 문서 | 영향 범위, 승인, 출시 구성과 해당 근거를 연결 |

[추적 링크](../trace/links.csv)는 해당 문서들에 정의된 ID의 관계를 기계가 확인할 수 있게 저장한다. 현재 초안은 기획→위험·가정→요구→설계·시험 명세까지 이어진다. 개발이 시작되면 `IMP`, `EVD`, `REL`을 같은 방식으로 연결한다. 초기 규칙은 정의되지 않은 ID, 고아 요구, 시험 없는 요구, 구현 출처 없는 변경, 증거 없는 출시 주장 또는 폐기 근거의 재사용을 검사하는 것이다. 코드 행 번호는 참고용이며 기준 근거는 식별자와 파일·커밋이다.

## 변경 요청에서 새 기준선까지

1. `CHG`를 등록해 변경 이유, 이전 기준선, 발의자, 영향받는 목표와 가정을 기록한다. 발생한 버그라도 최초 기획의 용도·운용 조건·의존성에서 영향 분석을 시작한다.
2. 시스템팀은 최초 영향 지점부터 기획과 위협을 다시 검토한다. 기능안전팀은 영향받는 위험, 안전 상태와 시간 배정을 재평가한다. 상위 전제가 유효하면 그 유지 근거를 남긴다. 기획이 달라지면 바뀐 기획을 먼저 작성하고 승인받는다.
3. 새 전제를 기준으로 요구사항, 인터페이스, 설계와 검증 계획을 전개한다. 영향받은 근거를 `재검증 필요`로 표시하고 검증 범위와 비영향 근거를 함께 제출한다.
4. 개별 개발팀과 통합팀이 같은 승인 기준선에서 작업한다. PR은 `CHG`, `REQ`, `DES`, `IMP`와 시험 영향을 연결하고 정확한 후보를 검증팀에 인계한다.
5. 검증팀이 새 결과를 발행하면 배포팀은 승인된 후보 해시와 확인 기록으로 출시한다. 이전 기준선과 그 증거는 당시 구성의 이력으로 보존한다.

예를 들어 Linux 장치를 가상 장치에서 실제 DMA 장치로 바꿀 때는 `OBJ-003`의 사용 조건, `ASM-002`의 보드 소유권, `HAZ-002`의 침범 가능성부터 다시 검토한다. 이후 `REQ-001`, `REQ-004`와 `DES-002`, 검증 `VER-001`, `VER-004`가 바뀐 조건을 반영했는지 확인한다. 기존 가상 장치 증거는 원래 범위에서 보관한다.

실제 작업에는 [변경 요청](../.github/ISSUE_TEMPLATE/change-request.md), [PR 인계](../.github/pull_request_template.md), [검증 증거](templates/verification-evidence.md) 양식을 사용한다.
