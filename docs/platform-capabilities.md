# J-NOX 플랫폼 기능 계획

한국어 · [English](platform-capabilities.en.md)

**기획 변경** `CHG-004` · 기준 리비전 `715b02f`. 표의 상태는 해당 리비전에 공개된 증거를 기준으로 한다. 이후 `CAP-001`의 동일 우선순위 FIFO에 대해 한 코어에서 양보·복귀를 확인했다. [변경 이슈 #18](https://github.com/Romanof123/JNOX/issues/18) · [EVD-003 FIFO 검증](evidence/evd-003.md) 후속 단일 코어 실행에서는 타이머가 양보하지 않는 동순위 스레드를 번갈아 실행하는 동작도 확인했다. [EVD-004 라운드로빈](evidence/evd-004.md)

이 기획 기준선은 J-NOX가 제공하려는 임베디드 실시간 운영체제 기능과, 검증팀이 어떤 동작을 관찰해야 지원 기능으로 표시할 수 있는지 정의한다. 제품별로 보드, 사용 사례와 구성을 선정한다. 안전성, 시간 한계, 호환성에 대한 판단 범위는 명시한 구성과 검증 근거로 정한다. [제품 목표와 마일스톤](product-plan.md) · [안전 가정](safety-security-concept.md)

**표 읽는 법.** 각 `CAP`에는 주 제품 목표 하나와 해당 기능의 일부를 다루는 기존 요구사항을 연결했다. 인수 기준에서 새로 정의한 동작은 구현 전에 요구사항, 설계, 검증 항목에 배정한다. **계획**은 인수 기준의 검증이 남아 있다는 뜻이다. **부분 근거**에는 이미 기록된 관찰 범위를 표시했다. **선택형**은 해당 기능을 채택한 구성에만 적용한다. 단계와 담당은 준비 책임을 나타내며, 검증팀은 후보와 증거를 독립적으로 검토한다. [요구사항](requirements.md) · [아키텍처](architecture.md) · [검증계획](verification-plan.md) · [추적 관계](../trace/links.csv)

M1에는 두 건의 초기 근거가 있다. 버전을 고정한 Rust 커널 ELF가 에뮬레이트한 Cortex-A72 코어 하나에서 부팅 시 규정된 UART 출력을 냈고, 두 차례 독립된 클린 빌드에서 동일한 해시가 나왔다. 별도 후보에서는 에뮬레이트한 코어 하나에서 두 스레드 사이의 타이머 선점과 복귀를 한 차례 관찰했다. 각 기록에 소스 후보가 명시되어 있다. 실보드 시간 한계, SMP, 프로세스 격리와 서비스 동작에는 아래의 별도 인수 기준을 적용한다. [EVD-001 부팅·빌드](evidence/evd-001.md) · [EVD-002 타이머 선점](evidence/evd-002.md)

새 인터페이스를 추가하거나 기능군의 누락을 보완할 때는 해당 CAP에 변경 건을 연다. 인터페이스 버전, 담당, 적용 구성, 상위 목표, 영향받는 요구사항과 측정 가능한 인수 기준을 명시한다. 부족한 요구사항·설계·검증 ID를 배정한다. 독립 검증을 마친 후보와 근거 수준을 붙여 지원 상태를 공개한다. [변경 관리](lifecycle.md)

### 구성별 자원 비용

확장 구성에서는 의존성이 허용하는 범위에서 런타임, 파일시스템, 네트워크 스택, 디버깅 도구, 드라이버 도메인, 주변장치를 개별 선택한다. 다중 스택, 노드 간 서비스, 외부 시각 동기화, 저전력 모드, 이중화, 동적 링크, 게스트 장치 할당은 각각 구성 채택 결정을 기록한다. 안전 기능이 사용하는 서비스는 의존 관계를 명시하고 해당 제품 범위에서 평가한다.

최소 안전 구성에는 커널, BSP, 제어 태스크 및 필요한 입출력·감시 경로의 버전을 고정한다. 선택한 서비스, 스택, 게스트, 주변장치를 구성 명세에 기록한다. 기능을 켠 빌드와 끈 빌드를 비교해 상주 RAM, 스택·풀 최대 사용량, 부팅 시간, IRQ·CPU 부하 및 명시한 보드에서 관찰한 최소 마감 여유를 기록한다. 시간 분석에 포함한 구성요소, 장치 DMA와 공유 버스 간섭을 명시한다. 제외한 구성요소는 엔드포인트와 권한이 제거되었는지 확인한다. 사용자 서비스, 펌웨어, 게스트 메모리, 영속 저장 공간은 별도 집계한다. ## 채택을 별도로 결정할 기능 제안

세 가지 확장에는 제품 차원의 명시적인 결정이 필요하다. PM은 사용자 수요, 담당팀, 비용 상한, 후보 구성, 시제품의 독립 검증 판정을 기록한다. 로드맵에 채택하려면 변경 기록, 승인된 요구사항과 배정된 마일스톤이 필요하다. 표의 기존 요구사항은 시제품의 의존성을 가리킨다.
