# Draft System Requirements

[한국어](requirements.md) · English

Each row is a candidate requirement awaiting approval. Safety analysis or board evaluation establishes the product-specific numerical limits. The rationale for each allocation must be traceable. The [architecture](architecture.en.md) defines the `DES` entries, and the [verification plan](verification-plan.en.md) defines the `VER` entries.

| Requirement | Source | Requirement and acceptance criteria | Design · Verification |
| --- | --- | --- | --- |
| `REQ-001` Spatial isolation | `HAZ-002`, `THR-001` | CPU writes, DMA writes, and device accesses may reach the control domain only through authorized paths. The system must contain invalid accesses and preserve the state of the safety domain. | `DES-001`, `DES-002` · `VER-001` |
| `REQ-002` Temporal isolation | `HAZ-001`, `HAZ-004`, `THR-001`, `OBJ-004` | Each configuration declares task periods, deadlines, execution budgets, and IRQ limits. Under the permitted load and concurrent interference, each response must meet its allocated time limit. An overrun must trigger the specified state transition. | `DES-003`, `DES-006` · `VER-002` |
| `REQ-003` Control data and fault response | `HAZ-003`, `HAZ-004`, `THR-001` | Check the length, range, version, sequence number, and freshness of control inputs. On termination, loss of response, or restart, notify the caller within a bounded time and perform the specified safety action. | `DES-002`, `DES-006` · `VER-003` |
| `REQ-004` Linux driver carry-over | `OBJ-003`, `ASM-002`, `ASM-003` | Reproduce the selected device's functionality on a compatible Linux configuration with the original driver source and binary unchanged. Record the versions and SHA-256 digests of the kernel, module, firmware, and device configuration. | `DES-002` · `VER-004` |
| `REQ-005` Threads and SMP | `OBJ-004`, `HAZ-001` | Run multiple threads in the same address space. Test thread creation, termination, waiting and cancellation, CPU affinity, synchronization, concurrent termination, and queue contention. The safety configuration must use the approved CPU assignment, counts, and policies. | `DES-001`, `DES-003` · `VER-005` |
| `REQ-006` Concurrent sockets | `OBJ-006`, `THR-003` | In the extended configuration, multiple processes and threads must use local sockets and TCP and UDP sockets over both IPv4 and IPv6 concurrently. Document nonblocking I/O, readiness notifications, concurrent reads and closure, connection and buffer limits, and backpressure. | `DES-005` · `VER-006` |
| `REQ-007` Scripting | `OBJ-006`, `THR-003` | Provide host-side build and test automation and target-side user-mode scripts. Enforce CPU, memory, and privilege limits on target scripts and allow their execution to be stopped. Validate the safety configuration statically at build time. | `DES-005` · `VER-007` |
| `REQ-008` Portability | `OBJ-005` | Each port must declare its level of support for CPUs, boards, memory protection, boot, IRQs, timers, SMP, DMA, real-time operation, and drivers. Each port must pass the common contract tests. | `DES-004` · `VER-008` |
| `REQ-009` Footprint | `OBJ-004` | Measure code and constant data in the minimal image, kernel RAM, stacks and static pools, initialization time, and latency on the physical board. The proposed reference ceilings for the minimal AArch64 configuration are 256 KiB for image code and constant data combined and 2 MiB for kernel RAM. | `DES-001`, `DES-004` · `VER-009` |
| `REQ-010` Boot and update trust | `OBJ-002`, `THR-002` | Authenticate boot images, configurations, and updates. Reject forged or revoked versions and versions that violate policy. Recover to an approved image after power loss. | `DES-007` · `VER-010` |
| `REQ-011` Least privilege and resource limits | `OBJ-002`, `THR-001`, `THR-003` | Declare permissions and resource limits for every service, device, socket, and script. Invalid requests and overload must preserve access controls and leave the safety domain's resources available. | `DES-001`, `DES-002`, `DES-005`, `DES-007` · `VER-011` |
| `REQ-012` Development and verification traceability | `OBJ-007` | For every requirement that applies to a release candidate, link its source, design, implementation, tests, evidence, and approval status. Evidence affected by a change can support acceptance of the new baseline once the reverification results or the rationale for reusing that evidence have been approved. | `DES-008` · `VER-012` |
| `REQ-013` Safety configuration suitability | `OBJ-001`, `OBJ-007`, `HAZ-004` | Make the safety manual, assumptions of use, exact hardware, compiler, boot, code and configuration versions, independent verification results, and residual risks available for review. | `DES-006`, `DES-008` · `VER-013` |
| `REQ-014` Development and observability APIs | `OBJ-006`, `OBJ-004` | Define the versions, errors, and supported configurations for the selected POSIX APIs and native IPC. Provide bounded diagnostic logging and platform timing instrumentation. Measure their overhead. | `DES-005`, `DES-006` · `VER-014` |
| `REQ-015` Native Rust drivers | `OBJ-008`, `HAZ-002`, `THR-001` | An unprivileged Rust service must use the SDK to handle requests and replies, device register access, IRQs, and authorized DMA buffers. Reject unauthorized mappings and requests that predate a restart. Other services must continue to operate. | `DES-009` · `VER-015` |
| `REQ-016` Rust implementation and toolchain confidence | `OBJ-008`, `OBJ-001`, `THR-002` | Implement the kernel core in `no_std` Rust. Review the locations and preconditions of `unsafe` code, the scope of the libraries, compiler and linker, the pinned versions, and evidence of reproducible builds. | `DES-001`, `DES-008`, `DES-009` · `VER-016` |
| `REQ-017` Security response and maintenance | `OBJ-002`, `THR-002`, `THR-003` | The security lead must define vulnerability intake, impact assessment, response prioritization, and notification criteria. The release team must verify the SBOM, provenance, and signatures and trace the safety changes and reverification associated with each patch. | `DES-007`, `DES-008` · `VER-017` |
| `REQ-018` Response to kernel, clock, and reset faults | `HAZ-004`, `ASM-001`, `ASM-002` | Allocate independent detection and output transition paths for each kernel halt, clock failure, monitoring-device failure, and reset failure assumed by the product. The time from detection to safe output must meet the product's allocation. Resume output according to the recovery conditions. | `DES-006` · `VER-018` |
| `REQ-019` Safety IPC channel | `OBJ-001`, `HAZ-003`, `THR-001` | Bind each safety channel to its authorized endpoints and data ID. Deliver data to the control task only after the receiver checks integrity, generation, sequence, issue time and validity interval. A rejected frame must leave the last valid value, issue time, sequence and rearm count unchanged. The receiver must evaluate expiry within its budget during sender silence, a continuous stream of invalid messages, or queue saturation. | `DES-010` · `VER-019` |

The footprint targets in `REQ-009` exclude boot firmware, user services, and the Linux image. Kernel RAM includes kernel objects, page tables, stacks, and reserve pools in the configuration profile. Record the image sizing method and link map at build time.
