# J-NOX 제품 기획 0.1

한국어 · [English](product-plan.en.md)

**상태**　검토용 초안 · 2026-11-23

J-NOX의 첫 제품은 제어 소프트웨어가 예측 가능한 시간 안에 실행되면서, 별도의 Linux에서 기존 장치 드라이버를 가져다 쓸 수 있는 임베디드 운영체제다. 첫 벤치 데모는 가상 입출력을 사용하는 주기 제어 태스크다. Linux 드라이버 서비스가 정상일 때는 데이터를 받아 처리하고, 지연·손상·정지가 생기면 J-NOX가 자체 타이머와 자체 권한으로 위험 출력 대신 정의된 대체 출력을 선택한다. 첫 제품의 실제 사용 사례와 안전 상태는 이후 시스템 수준 분석에서 정한다.

## 제품 목표

제품 기능은 프로파일별로 할당하고, 기능별 합격 조건과 현재 증거를 함께 추적한다. 기본 기능과 채택 검토 중인 추가 제안은 기능표에서 확인할 수 있다. [플랫폼 기능 기준선](platform-capabilities.md)

안전 태스크가 다른 태스크나 Linux 게이트웨이에서 제어 데이터를 받을 때 선택할 수 있는 안전 IPC 채널을 계획한다. 첫 사용 사례는 가상 출력 허가다. 수신자는 마지막으로 수락한 허가가 만료되면 독자적으로 출력을 차단한다. [안전 IPC 요구사항](requirements.md)

기능안전팀은 첫 소프트웨어 벤치에서 허가 신호 상실 시 가상 출력을 차단하는 기준을 `ADR-001`에 고정했다. 이를 첫 제어 태스크와 시험의 설계 입력으로 사용한다. 제품 적용 시 기능안전팀과 시스템팀은 실제 운용 조건과 위험 분석으로 안전 상태 및 시간 한계를 도출한다. [첫 벤치 결정](safety-parameters.md)

| ID | 목표 | 최초 성공 기준 |
| --- | --- | --- |
| `OBJ-001` | 지정한 자동차 시스템에서 ASIL D 안전 목표 지원 | 적용 시스템, 가정, BSP·툴체인·빌드 구성을 특정해 안전 논증과 검증 증거를 독립 검토할 수 있다. |
| `OBJ-002` | 높은 사이버 복원력과 제품 수명주기 운영 | 위협별 완화와 검증을 추적하고, Linux 도메인 침해 가정에서도 경계와 안전 기능을 검증한다. 서명 부팅·업데이트·복구를 재현한다. |
| `OBJ-003` | 기존 Linux 드라이버 변경 없는 이관 | 지정 장치 하나를 Linux 드라이버 소스·모듈 수정 없이 가져와 J-NOX에서 서비스를 이용한다. 드라이버 중단·Linux 재시작 중의 제어 동작까지 시험한다. |
| `OBJ-004` | 작은 커널, 하드 실시간, 멀티스레드 | 최소 이미지 자원 사용량과 실보드 최악 구성에서의 제어 태스크 시간 한계를 제시하고, 지원 스케줄링과 스레드 동작을 재현한다. |
| `OBJ-005` | Arm 전 프로파일과 x86 계열로 확장 | 공통 커널·서비스 계약을 유지하고, 각 CPU·보드 조합에 대해 부팅·기능·실시간·안전 검증 상태를 명시한다. |
| `OBJ-006` | Rust·C 앱과 기존 Linux CLI를 지원하는 서비스 환경 | J-NOX SDK로 빌드한 네이티브 Rust 앱과 C 앱을 실행한다. 확장 구성에서는 지원 목록에 있는 기존 Linux 사용자 실행 파일도 같은 CPU 아키텍처에서 재빌드 없이 직접 실행한다. 멀티스레드 소켓, 진단·자동화 스크립트와 선정한 POSIX API를 제공한다. |
| `OBJ-007` | 계획을 기준으로 변경하고 근거를 재현 | 각 요구가 기획 또는 위험에서 출발해 설계·구현·시험·증거로 이어지고, 결과에서 원래 의도를 거슬러 확인할 수 있다. |
| `OBJ-008` | Rust 기반 커널과 J-NOX 네이티브 드라이버 생태계 | 타깃별 툴체인 범위와 `unsafe` 경계를 검토하고, 네이티브 Rust 드라이버와 SDK를 독립적으로 검증한다. |

## 구성과 지원 범위

- **안전 구성.** 안전 태스크, 커널, 필요한 BSP와 최소 입출력 경로, 적용 시 격리·감시 구성요소를 버전 고정한다. 태스크·메모리·IRQ·CPU 예산은 시스템 설정으로 확정한다. 첫 ASIL D 적용 후보는 한 보드와 한 사용 사례로 잡는다.
- **확장 구성.** 같은 커널 계약 위에서 사용자 서비스, Linux 드라이버 도메인, 소켓, 스크립트, 파일 서비스와 개발 도구를 선택한다. 보드·용도별로 필요한 부분을 조합한다.
- **기기 지원.** 포트가 빌드되는 상태, 에뮬레이터 부팅, 실제 보드 기능 검증, 제품 안전 근거가 확보된 상태를 각각 기록한다. 보드 교체 시 타이머·인터럽트·DMA·리셋·메모리 간섭 근거를 다시 본다.

| 순서 | 포트 | 실험·지원 범위 |
| --- | --- | --- |
| P1 | Arm AArch64 Cortex-A72/A76 · QEMU `virt` | 기준 커널 동작, MMU, EL0/EL1, 선점, IPC. 가상 결과를 실보드 시간 자료에 인용할 때는 환경을 표시한다. |
| P2 | Arm Cortex-R52 · QEMU MPS3-AN536와 실제 보드 후보 | AArch32·MPU 포트와 주기 제어. R-Car V4M은 A76 Linux와 R52 J-NOX 조합 후보이며, 보드 확보와 리소스 제어 가능성을 먼저 검토한다. |
| P3 | x86-64 · QEMU 후 실기기 | UEFI/ACPI, APIC, 타이머, SMP, 지원 장치의 IOMMU 검증. Linux 도메인 격리 후보 평가. |
| P4 | Arm AArch32, 기타 Cortex-R·Cortex-M, IA-32 | 대표 코어·보드를 정해 능력 매트릭스를 확장한다. MPU 부족 또는 보호 장치 제약이 있는 보드는 가능한 기능 구성과 필요한 외부 격리를 명시한다. |

Arm의 A/R/M 프로파일과 x86의 모드·장치 차이를 BSP 계약에 반영한다. R-Car V4M의 실제 부팅, 리셋 소유권, DMA 격리 가능성은 보드 검증 항목이다. [Arm 아키텍처](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Introducing%20the%20Arm%20architecture.pdf) · [Intel 시스템 프로그래밍 매뉴얼](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html) · [Renesas R-Car V4M](https://www.renesas.com/en/about/newsroom/renesas-leads-adas-innovation-power-efficient-4th-generation-r-car-automotive-socs)

## 단계별 승인 산출물

| 단계 | 제출물 | 완료 조건 |
| --- | --- | --- |
| M0 기획 | 제품 기획, 안전·보안 개념, 요구사항, 설계안, 검증계획, 추적 링크 | 문서 관계를 검토하고 첫 벤치 시나리오와 미정 항목을 기록한다. |
| M1 커널 | 첫 AArch64 빌드, 태스크·스레드 생명주기, 고정 우선순위 선점, 타이머, 메모리 격리, IPC | 동일 커밋에서 반복 가능한 QEMU 시험과 부정 시험을 통과한다. |
| M2 드라이버 | 실제 Linux와 이관 드라이버 1종, 네이티브 Rust 드라이버 1종, SDK·도메인 간 프로토콜과 장애 시험 | 양쪽 경로의 계약을 각각 검증하고, Linux가 멈춰도 벤치 제어가 정해진 동작으로 이어진다. |
| M3 이식·실기기 | R52 보드 시험, x86-64 기준 포트, 부하·고장 주입, 스레드·SMP 증거 | 선정 보드에서 시간·메모리·DMA·재시작 경계를 측정하고, CPU별 근거를 분리해 기록한다. |
| M4 서비스·운영 | 네이티브 Rust·C SDK, Linux 사용자 공간 ABI, POSIX API, 병행 소켓, 스크립트, 보안 업데이트·복구 | Rust 앱 실행, C 프로그램 간 파이프, 기존 Linux CLI 직접 실행을 각각 입증하고 API 계약과 자원 제한을 검증한다. AArch64 정적 실행을 먼저 검증한다. x86-64와 동적 Linux ELF는 각각 별도 호환성 시험을 거친다. 안전 구성은 선정한 의존성만 승인 대상으로 삼는다. |
| M5 제품 안전 근거 | 첫 제품 구성의 안전 매뉴얼, 잔여 위험, 구성 기준선, 독립 검토 패키지 | 기획과 실제 적용 조건이 일치하는지 확인하고 ASIL D 안전 목표 지원 근거와 보안 근거를 해당 범위에서 심사받는다. |
| M6 추가 이식 | P4 대표 보드별 포팅 계획과 검증 증거 | 시스템팀이 Arm AArch32, 추가 R/M 계열 및 IA-32 보드별 자원과 보호 전제를 승인한다. 공통 부팅·격리·스케줄링 시험과 해당 보드의 추가 시험을 통과한 범위대로 지원 상태를 갱신한다. |

M0에서 결정할 항목은 첫 제품 적용 사례와 운용 환경, 첫 실보드와 Linux 장치, 안전 상태와 허용 고장 반응 시간, 하드웨어 안전 매뉴얼 접근, 안전·보안 검토 책임이다. 결정 시 해당 기획·가정 ID에서부터 후속 문서로 근거를 전개한다.
