# EVD-112 · Native application monotonic clock

CHG-112 / IMP-112 / [#286](https://github.com/Romanof123/JNOX/issues/286) / [#288](https://github.com/Romanof123/JNOX/pull/288)

On original source `46a87fb7177e748963726f44f262525a51d865fd`, the shipped C and Rust applications made both monotonic clock calls, checked their checksums and exited 0. The linked code performed the final checksum operations after the second read, so those first samples cover only part of the calculation. A separate Rust Cargo application retained its own clock samples. A separate 16-read application exited normally. The legacy C probe exited 37 and its write returned −38 (ENOSYS).

Source `7af3ca22b88c9ea9d81f4495b37613f241b67adc` changes the two examples to store the complete checksum before the closing read. Both versions use the same kernel and SDK.

On the corrected source, both applications exited 0 on their first single-core Cortex-A72 QEMU virt boots. Each made two successful EL0 clock calls around the completed checksum store. C retained both timespecs in RAM: (0 s, 1,715,056 ns) and (0 s, 2,014,704 ns), and checked Adler-32 `0x11e60398`. Rust reused its result buffer. Its first nanoseconds (1,716,736) survived in saved x20. The first seconds value of zero follows from the SDK range check, the successful order check and the observed final seconds of zero. The final Rust pair (0 s, 1,989,488 ns) and FNV-1a checksum `0x4f9f2cab` were read from stopped RAM. The separate 16-read control retained all 16 normalized increasing timespecs after the diagnostic journal reached its eight-event capacity. These results cover ordinary boot-domain monotonic reads on the emulator.
