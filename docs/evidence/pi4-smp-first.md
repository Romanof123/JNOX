# Pi 4 모델의 두 차례 콜드 부팅과 코어 간 깨우기

[English](pi4-smp-first.en.md) · [기계 판독 결과](pi4-smp-first.json) · [증거 묶음](pi4-smp-first.zip)

같은 원시 이미지로 처음 실행한 두 번의 부팅에서 CPU0가 합계 136과 392를 보냈다. CPU1의 대기 중인 수신 태스크는 세대마다 한 번 깨어나 각각 272와 784를 반환했다. 네 차례 모두 백그라운드 실행이 PC 0x82698, SP 606144에서 중단되었고 수신 태스크의 SVC 후 같은 PC와 SP에서 재개되었다. 세 태스크의 스택 가드가 보존되었고 CPU0의 10개 기록과 CPU1의 28개 기록이 각 부팅에서 손실 없이 커밋되었다. [검증 대상 소스](https://github.com/Romanof123/JNOX/tree/d537835a858bb340c3a8d8507fb7bd5ec3ad20c4)

| 부팅 / 세대 | 전송 전 CPU0가 읽은 진행 값 | CPU1 중단 → 재개 후 진행 값 | CPU0 전송 호출 틱 |
|---|---|---|---:|
| 1 / 1 | 960 → 16384 | 27024 → 27056 | 4977 |
| 1 / 2 | 28352 → 28576 | 29680 → 29712 | 2263 |
| 2 / 1 | 400 → 15520 | 26496 → 26528 | 5475 |
| 2 / 2 | 27440 → 27792 | 29184 → 29216 | 2173 |

CPU0 생산자 진입 PC는 0x827e0, CPU1 수신자 진입은 0x82c90, 첫 백그라운드 진입은 0x8261c였다. 매 세대 CPU1은 송신 CPU가 0인 IAR 1을 읽고 수신 태스크를 대기에서 준비로 전환했다. 전체 IAR 값으로 EOI 후 저장된 수신 PC 0x82d78로 복귀했다. 백그라운드와 수신 태스크의 832바이트 프레임 시작 주소는 각각 605312와 621728, SP는 606144와 622560이었다. Rust의 실행 지점 기록과 MPIDR를 링크 결과와 대조했다. QEMU 스레드별 원본 로그의 예외 및 복귀 PC는 스레드 ID와 Linux 태스크 이름으로 vCPU에 연결된다. mapping.json에는 1부터 시작하는 원본 줄 번호가 있다. CPU2와 CPU3의 TCG 스레드도 확인되었고 두 코어의 태스크 예외·복귀 기록은 없었다.

구현을 읽기 전에 독립 검증 절차를 고정했다. Rust 1.95.0의 AArch64 베어메탈 타깃과 전용 Pi 4 SMP 설정으로 첫 release 빌드가 경고 4건과 함께 성공했다. 매회 코어 4개, 메모리 2 GiB의 새 raspi4b TCG 프로세스를 사용했다. 관측 상한은 30초였고 마지막 직렬 출력 후 1초 이상 기다린 뒤 호스트에서 종료했다. 호스트 경과 시간은 각각 1.157초와 1.139초였다. 두 코어의 카운터 주파수는 모두 62.5 MHz였다. 표의 틱은 로컬 소프트웨어 전송 호출 구간이다. 버스 전달 시간, 코어 간 지연과 공통 시각 기준은 확인되지 않았다. 두 캡처 각각에서 CPU·세대·IAR 송신자 변조와 IRQ 행 삭제를 호스트 재생기가 모두 검출했다.

묶음에는 UART·스레드 로그 원본, 관측 스크립트, 사전 고정 절차, ELF, 원시 이미지, 링크 맵, 디스어셈블리, 펌웨어 패키지 입력, 빌드 출력, 해시 목록과 재생 도구가 들어 있다. prefreeze.sha256에서 실행 파일·소스 tar·패키지 입력의 SHA-256을 확인할 수 있다. 빌드 로그·사전 해시 목록·종료 기록 두 건에서 로컬 경로를 줄인 내역과 원본 및 공개 파일 해시는 path-substitutions.json에 있다. 같은 ELF·이미지·UART는 한 번씩 저장했다. ZIP을 풀고 Python 3에서 pyelftools를 사용할 수 있게 한 뒤 `python reconstruct.py`를 실행하면 두 재생 폴더를 구성한다. 모델은 원시 커널을 직접 로드하므로 동봉한 부팅 펌웨어는 실행되지 않았다. 실물 보드 기동, 하드웨어 타이밍, 에너지, 간섭, WCET 및 제품 배치는 미검증 상태다.
