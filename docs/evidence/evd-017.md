# EVD-017 · CPU0에서 중단한 작업을 CPU1에서 재개

[English](evd-017.en.md) · [합격 기준](../m3-smp.md) · [변경 이슈 #47](https://github.com/Romanof123/JNOX/issues/47)

독립 검증자 두 명이 같은 Rust 이미지를 Cortex-A72 가상 CPU 두 개의 QEMU 6.2.0 virt에서 각각 처음 부팅했다. 두 실행 모두 CPU0의 타이머가 M을 `0x40201304`에서 중단했다. CPU1이 같은 명령 주소와 전용 스택, TLS, SIMD 및 루프 카운터를 복구했다. CPU0에서는 그곳에 고정된 대체 작업이 실행됐다. 고정 배치 및 단일 CPU 클러스터 시험에서도 각 작업이 허용된 CPU에서만 실행됐다. 각 검증자는 11개 실행권 구간을 작업별 합계와 대조하고, 이미 실행 중인 M의 중복 인수와 클러스터 밖 인수가 모두 거부됐음을 확인했다.

| 최종 구성의 첫 부팅 | 가상 CPU 두 개의 호스트 스레드 | IRQ 진입부터 목적 작업 콜백까지 | 결과 |
| --- | --- | ---: | --- |
| 멀티스레드 TCG | 495, 496 | 1,033.888 µs | 통과. [UART·QMP·작업 이력·예외 기록](evd-017-multi.json) |
| 단일 스레드 TCG | 497, 497 | 1,029.792 µs | 통과. [UART·QMP·작업 이력·예외 기록](evd-017-single.json) |

각 실행에서 PSCI 호출 한 번, IRQ 한 번, SVC 열 번을 관측했다. 62.5 MHz 카운터로 잰 각 간격에는 스케줄러와 계측 코드가 소비한 시간이 포함된다. QMP로 호스트 스레드 번호를 확인하고, 작업 이력으로 CPU를 식별했으며, 예외 기록으로 저장·복귀 주소를 교차 확인했다. 수치는 모드별 가상 실행 한 번의 측정값이다. 실물 이동 지연·공유 캐시 간섭·제품별 합격 기준·기능안전 승인은 별도 추적한다.

첫 후보는 멀티스레드 시험을 통과했지만 단일 스레드에서 5초 제한을 넘겼고, 제한을 12초로 늘린 진단 실행도 만료됐다. 상대 CPU를 기다리는 루프에 AArch64 YIELD를 명시한 뒤 원래의 5초 제한에서 두 CPU가 모두 진행했다. 초기 실패와 진단 기록을 보존했다. [첫 후보 기록](evd-017-initial.json) · [QEMU의 YIELD 처리](https://github.com/qemu/qemu/blob/v6.2.0/target/arm/op_helper.c#L327-L336)

최종 통합 검사에서 Rust 호스트 시험 63개, 응답시간 분석 시험 8개, 순차 게스트 회귀 11회가 통과했다. 통합 스크립트의 경로 오류로 최소 부팅 ELF를 SMP 관찰기에 입력한 별도 실행에서는 요구 표식이 누락돼 실패했다. 스크립트를 수정하고 다섯 가지 빌드 조합을 각각 실제 출력 경로의 ELF로 재실행했다. [회귀 시험과 잘못된 이미지 실행](evd-017-regressions.json)
