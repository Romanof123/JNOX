# EVD-107 · Pi 4 지정 코어 인계

CHG-107 / IMP-107 / POL-013 / [#280](../boards/pi4-typed-handoff.en-ko.md) / [#281](https://github.com/Romanof123/JNOX/pull/281) / [#47](https://github.com/Romanof123/JNOX/issues/47) / [#21](https://github.com/Romanof123/JNOX/issues/21)

공개 MG4 판독기로 PR #281의 고정 소스 `84214dd36094b4b3b489ab0232e9aa2f4774260b`에서 최초 부팅 12회를 채점했다. 짧은 작업 6회 모두 종료 코드 `0x1d`로 조기 종료했다(0/6). 이 기록으로는 인계 소비 여부와 종료 시점 RAM의 슬롯 상태를 확인할 수 없다. 스트림은 6/6 통과했다. 봉인된 추적 기록 6개에서 개시·역방향 인계의 소비, 선택된 프레임과 이후 작업 실행을 확인했다. global 2회에서는 CPU0에서 인터럽트된 M이 CPU1에서 재개했다. partitioned 2회와 clustered 2회에서는 M이 CPU0에서 재개했다.

별도 진단 부팅 2회는 12회 점수에서 제외했다. D1(짧은 clustered)에서는 개시 인계 게시를 관측했고 종료 시점 RAM에서 개시 슬롯은 Pending, 역방향 슬롯은 Empty였다. D2(스트림 global)에서는 두 슬롯 모두 Consumed였다. 선택된 M 프레임은 IRQ에서 저장한 버전 2였고 교체 P1 프레임은 새로 만든 버전 2였다.

앞선 #279 MG3 집단은 짧은 작업 3/6, 스트림 6/6을 통과했다. 두 집단의 결과만으로는 타이밍 개선이나 조기 종료 원인을 판정할 수 없다.

정책별 채점 2회 모두 M의 IRQ와 목적지 ERET에서 일치한 PC는 global `0x82cb0`, partitioned `0x82cb4`, clustered `0x82d40`였다. 역방향 인계는 모두 CPU1 리스 4를 선택했다. global에서는 IRQ에서 저장한 M 프레임 버전 2를, 두 고정 정책에서는 새 교체 P1 프레임 버전 2를 선택했다.

D1은 저널 30행, D2는 72행을 보존했다. D2에서 CPU0 IRQ와 CPU1 ERET의 PC가 `0x82cf0`으로 일치했다. 이는 루프 범위에서 제외되는 끝 주소여서 원격 복귀는 엄격한 내부 루프 조건을 충족하지 않았다. 두 진단 모두 저널과 초기 스택 경계에서 재구성한 256바이트가 종료 시점 RAM과 일치했다.

Rust 전이 거부 시 이전 상태 보존 검사는 5/5, Python 인계·진단 검사는 6/6 통과했다. 판독기는 버전을 낮춘 MG4 표식을 거부했고 과거 30회(MG1 6회, MG2 6회, MG3 12회, CRC 6회)의 원본을 다시 읽었다. 일반 QEMU SMP에서 예상 출력이 확인됐다. SW1 최초 오프라인 판독은 pyelftools 누락으로 실패했고 의존성을 갖춘 판독기로 같은 최초 부팅 기록에서 CPU별 PC 일치를 확인했다. 실제 Pi 4 검증은 남아 있다.
